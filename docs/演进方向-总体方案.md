## 一、线 1 · GitHub 专业性：架构图到底要不要画？

### 结论：**要，而且是三层**（只贴一张图是不够的）

很多人只放一张架构图就觉得专业了。实际上招聘方看 README 的顺序是：**一眼看懂是什么 → 技术栈是否匹配 → 有没有工程细节 → 代码质量**。所以图要分三层铺：

| 层 | 放什么 | 用在哪 | 为什么 |
|---|---|---|---|
| **第 1 层：视觉锚点** | 一张**美化过的架构图**（SVG，粉彩风格和产品视觉一致）+ 3~5 张界面截图/动图 | README 顶部 | 决定要不要继续往下看。纯 ASCII 图在这一层不够 |
| **第 2 层：可维护的图** | **Mermaid 图**（原生渲染，改代码顺便改图） | README 主体 / `docs/` | 招聘方会看你"图会不会过期"。ASCII 图和代码容易脱节，Mermaid 不会 |
| **第 3 层：工程细节** | 核心流程时序图、数据库 ER 图、模块依赖图 | `docs/architecture.md` | 证明你真的理解自己的系统，而不是套模板 |

> Mermaid 在 GitHub README 里**原生渲染，不用任何插件**。这是性价比最高的一层。

### 建议的 README 结构（按招聘方的阅读动线排）

```
1. 标题 + 一句话定位 + Badge（build 通过 / Java 21 / 测试数 / license）
2. 演示区：1 张架构总图 + 3 张界面截图（导入 / 刷题 / AI 助手）
3. 核心特性：3~5 条，每条一句话，不写"实现了 XX"而写"解决了什么"
4. 技术栈表（一眼看出匹配不匹配 JD）
5. 系统架构：Mermaid 分层图 + 模块依赖方向
6. 核心流程：导入流水线 / 刷题 / AI 对话 —— 三张 Mermaid 时序图
7. 数据库设计：Mermaid ER 图 + 关键表说明
8. 快速开始：一条命令跑起来（docker-compose 或脚本）
9. ⭐ 设计亮点：4~6 条"我为什么这么设计"（这是最能体现水平的一节）
10. ⭐ 性能与质量数据：识别率 / 接口耗时 / AI 成本对比
11. Roadmap（未实现的部分，写清楚边界比假装完整更专业）
12. License
```

### 第 9、10 节是杀手锏

| 亮点条目 | 素材（你项目里真实存在的） |
|---|---|
| 「为什么不用 ORDER BY RAND()」 | 已有注释说明，补上数据对比 |
| 「为什么规则优先、AI 兜底」 | 已有完整论述，写成"成本/可控性权衡" |
| 「为什么 BYOK 每请求造模型」 | 已有论述，是很好的"多租户隔离"思路 |
| 「为什么 AI 抽取按题目边界分块」 | 已有论述 |
| 「为什么导入用独立事务记失败」 | 已有论述，是事务边界的经典案例 |
| **「识别率从 X% 到 Y%」** | **需要线 2 做出来（这是新增的、最有冲击力的）** |

### 顺手做的工程化门面（低成本高感知）

| 项 | 成本 | 效果 |
|---|---|---|
| GitHub Actions：push 自动 `mvn test` | 低 | Badge 直接显示"测试通过"，**现在测试是红的必须先修** |
| 把测试数从 31 提到 100+ | 中 | Badge 上写"128 tests passing"很唬人 |
| `docker-compose.yml`（MySQL + 应用） | 低 | "一条命令跑起来"，招聘方真的会试 |
| 截图/GIF 放 `docs/images/` | 低 | README 视觉质感提升最大的一步 |
| Issue/PR 模板、CONTRIBUTING | 极低 | 细节分，锦上添花 |

## 二、线 2 · 题库识别攻坚（你提的重点）

### 2.1 先说清现状的**根本问题**

我读完了 [QuestionParser.java](asteria-common/src/main/java/com/asteria/common/Tool/QuestionParser.java) 全文（395 行）和三个 Reader。结论：

> **当前架构是"先把文档拍扁成纯文本，再用正则从纯文本里把结构猜回来"。**
>
> 文档里本来明确存在的结构信息（Word 的段落样式、标题级别、表格边界、PDF 的字号/栏位），在 `XWPFWordExtractor` / `PDFTextStripper` 这一步被全部丢掉了，之后只能用文本特征去反推。

这带来四个具体瓶颈：

| # | 瓶颈 | 证据 | 后果 |
|---|---|---|---|
| B1 | **表格里的题全丢或串行** | `DocxTextReader` 用 `XWPFWordExtractor`，表格单元格被拉平成文本 | 题库文档大量用表格排版（题干一列、选项一列）→ 识别失败 |
| B2 | **无法区分"标题"和"正文"** | `matchChapter` 只能靠长度 ≤30 字、不含句末标点两重启发式（[:240-242](asteria-common/src/main/java/com/asteria/common/Tool/QuestionParser.java#L240-L242)） | 标题被吞成题干 / 题干被误判成章节，两种错都发生过 |
| B3 | **PDF 双栏和多栏必乱** | `PDFTextStripper` + `setSortByPosition(true)`（[PdfTextReader.java:26](asteria-server/src/main/java/com/asteria/server/tool/PdfTextReader.java#L26)）只能处理单栏 | 双栏教材 PDF 抽出来的文本是交叉的 |
| B4 | **扫描件/图片题 = 0** | `PdfTextReader` 注释自认"扫描件抽不出任何文字" | 大量 PDF 题库直接不可用 |

另外 `QuestionParser` 内部还有几处**规则覆盖不全**（不是因为架构，是正则太窄）：

| # | 覆盖不到 | 位置 |
|---|---|---|
| G1 | 题号 `①②③`、`一、`（章节序号当题号）、`1)`（半括号） | `QUESTION_HEADER` [:9-10](asteria-common/src/main/java/com/asteria/common/Tool/QuestionParser.java#L9-L10) 只认 `【第N题】`/`（N）`/`N、N. N．` |
| G2 | 题型小节词表窄：没有 `名词解释` `论述题` `计算题` `案例分析` | `SECTION_TYPE_PATTERN` [:28-30](asteria-common/src/main/java/com/asteria/common/Tool/QuestionParser.java#L28-L30) |
| G3 | 答案格式：`【答案】` `答案：A`（单独"答案"被故意排除） | `ANSWER_INLINE_PATTERN` [:88-89](asteria-common/src/main/java/com/asteria/common/Tool/QuestionParser.java#L88-L89) |
| G4 | 填空题占位符 `（  ）` 不参与判型 | 判型靠"没有选项 + 答案短" |
| G5 | 一行多个选项的情况（`A.甲  B.乙  C.丙`） | `OPTION_PATTERN` 要求整行匹配 |

### 2.2 改造方向：**结构化管道（Structured Ingestion Pipeline）**

核心思路：**不要在纯文本上猜结构，而是在有结构的时候就保留结构。**

```
现在：  docx/pdf/txt ──► String（拍扁）──► 正则切题 ──► RawQuestion
                                  ↑
                            结构信息在这里丢失

改后：  docx/pdf/txt ──► DocBlock 模型（保留结构）──► 切题器 ──► RawQuestion
                        ┌────────────────────────┐
                        │ DocBlock {             │
                        │   text                 │
                        │   type: HEADING/PARA/  │
                        │         TABLE_CELL/LIST│
                        │   headingLevel         │   ← Word 样式给的真实层级
                        │   styleName            │   ← "标题 1" / "题干" 自定义样式
                        │   tableId / row / col  │   ← 表格坐标
                        │   fontSize / bold      │   ← PDF 用来推标题
                        │   page / column        │   ← PDF 分栏
                        │ }                      │
                        └────────────────────────┘
```

有了这层，三条瓶颈直接消失：

| 瓶颈 | 解决方式 |
|---|---|
| B1 表格 | `XWPFTable` 单独遍历，**按行重组单元格**（题干 + 选项在同一行 = 一道题） |
| B2 标题判定 | 直接读 Word 段落样式（`Heading 1` / 自定义样式），**不用再猜长度和标点** |
| B3 PDF 分栏 | 用字号的众数当正文基准、超过阈值的当标题；按 x 坐标聚类分栏后**逐栏阅读**，而不是全页排序 |
| B4 扫描件 | 接入 **OCR 兜底**：先判断"抽取到的文字密度"，过低则走 OCR（Tesseract Java 封装 / 云端 OCR 可选） |

### 2.3 但更重要的：**先把"识别率"变成可测量的数字**

这是我强烈建议你先做的一件事，**它比任何算法改进都重要**：

> 现在你无法回答"识别率是多少"，所以任何改进都无法证明有效，简历上也无话可写。

**做法**：

```
1. 建一个 golden 数据集：手工标注 3~5 份真实题库的期望结果
   （题目数 / 每题的 题干·选项·答案·题型 / 章节归属）
   → 这是唯一标准答案，放进 test resources，随代码走

2. 写一个"识别率评测器"：
   对每份文件跑导入，逐字段比对，输出：
   ┌──────────────────┬────────┬────────┬────────┐
   │ 字段              │ 命中    │ 总数    │ 准确率  │
   ├──────────────────┼────────┼────────┼────────┤
   │ 题目切分（题数）    │  48    │  50    │ 96.0%  │
   │ 题干              │  47    │  50    │ 94.0%  │
   │ 选项              │  44    │  50    │ 88.0%  │
   │ 答案              │  45    │  50    │ 90.0%  │
   │ 题型              │  49    │  50    │ 98.0%  │
   │ 章节归属          │  50    │  50    │100.0%  │
   └──────────────────┴────────┴────────┴────────┘

3. 改进前后各跑一次 → 简历上就是：
   「建立字段级识别率评测体系，题库解析准确率从 78% 提升至 94%」
```

**为什么这个最值钱**：它把"我觉得好用了"变成"数据证明好用了"，这是**工程思维 vs 学生作业**的分水岭。

### 2.5 深度调研结论（已核实到一手来源）

我针对"为什么识别不准"做了专项调研，有 8 条结论能直接落到代码上：

#### ① 切题换个方向：选项锚点回溯法 ⭐ 最值得抄

[qba-js](https://github.com/enncy/qba-js) 的核心算法**不正向匹配题号**，而是反向：

```
先找「^A 且下一行 ^B」的选项起点  →  向上回溯到最近的题号行  →  中间部分就是题干
```

**为什么这招强**：题号可以有一百种写法（`1.` `1、` `（1）` `①` `一、`…），我们现在的 `QUESTION_HEADER` 正则就是在穷举这个；但**"选项一定是 A/B/C/D 连续出现"是强得多的结构信号**。这一招能直接救回"题号格式不认识 → 整份文件一道题都切不出"的场景。

落地成本：**低**（约 50 行 Java 状态机），可以和我们现有正向解析**并存做双通道**，谁切出的题多/更完整用谁。

#### ② Handler 预处理链：把"脏文本清洗"和"核心解析"解耦 ⭐

[qba-js](https://github.com/enncy/qba-js) 用 `before()/after()` 钩子把清洗规则做成**可插拔的 Handler**。我们现在的 395 行 `QuestionParser` 里，清洗逻辑和切分逻辑是混在一起的——**每加一所学校的格式就要动核心代码，回归风险高**。

它内置 handler 里已经**被生产验证过**的真实脏数据规则（可直接搬成 Java）：

```java
.replace("．", ".")                          // 全角句点
.replace("窗体底端", "").replace("窗体顶端", "")   // ← Word 表单域残留，我们一定会遇到
.replace("第N次作答", "")                      // 平台作答次数水印
.replaceAll("必做.*?题量.*", "")               // 超星类平台水印
.replaceAll("我的答案.*?(正确答案|标准答案)", "$1")  // 「我的答案」在「正确答案」上方
.replace("正确答案为", "正确答案：")             // 换一种标签说法
.replace("[正确答案]", "正确答案：")             // 再换一种
.replaceAll("第[一二三四五六七八九十]空", "#")     // 多空填空的分隔
.replace("●", "")                            // ← Word 复制的选项带项目符号
```

> 最后两条尤其相关：`● A xxx` 是**从 Word 复制题库时的常见形态**，而 `窗体顶端/底端` 是 Word 文档导出时的常见残留。

#### ③ 答案区二次配对（双 pass）

教辅书和考试系统导出**经常是"题目在前、答案统一在文末"**。我们现在的裸答案行逻辑只处理**紧邻**的答案，跨距离配对会失败。

`qba-js` 的做法：第一遍只切题、把答案区按顺序入队；**第二遍遍历还没有答案的题，按顺序取队列配对**。落地成本：**低**。

#### ④ 按"组成成分"判型，而不是等小节标题

我们现在强依赖 `1．选择题` 这类小节行，**文档没有小节标题时全部退化**。

有中国专利支撑的判据（[CN117150020A](https://patents.google.com/patent/CN117150020A/en) §[0134]，旁证 [CN105488171B](https://patents.google.com/patent/CN105488171B/zh)）：

```
组成成分 = 题干 / 选项 / 答案 哪些存在
  只有题干 + 题干含括号或下划线  → 填空题
  有选项 + 答案字母数 == 1      → 单选题
  有选项 + 答案字母数 >= 2      → 多选题
  只有题干 + 答案是对错词        → 判断题
```

**即"看到什么组成"而不是"看到什么关键词"**。建议作为小节标题判定的**低优先级兜底**。

另外 `qba-js` 的题型元信息正则 `(.{2,4}题)` **不枚举题型词**——它通吃 单选/多选/判断/填空/简答/名词解释/论述/计算题。**新增题型无需改正则**，比维护白名单抗变化。

#### ⑤ Word 里的表格：POI 有个"官方级"的坑

我们的 `DocxTextReader` 用 `XWPFWordExtractor`，表格被拉平——这是 B1 瓶颈的根源。

调研确认：**`XWPFTableCell` 的 `getParagraphs()` 和 `getTables()` 各自返回全集，无法还原它们交错出现的真实顺序**（[Stack Overflow](https://stackoverflow.com/questions/62587586/trouble-extracting-all-elements-of-docx-tablecell-in-correct-order-with-apache-p)，⚠️ 该问题 **0 个答案**——说明这是公认的坑但没现成解法）。

**正解是用 `IBody` 抽象**：

```java
// XWPFDocument / XWPFTableCell 都实现了 IBody
for (IBodyElement el : body.getBodyElements()) {     // ← 按文档顺序
    if (el.getElementType() == BodyElementType.PARAGRAPH) { ... }
    else if (el.getElementType() == BodyElementType.TABLE) { ... }
}
```

**同一套代码可以递归处理正文和表格单元格**（[IBody API 文档](https://svn.apache.org/repos/asf/poi/site/publish/apidocs/4.0/org/apache/poi/xwpf/usermodel/IBody.html)）。这就是 `DocBlock` 管道的实现基础。

> 另一个坑：**Word 文本框**（`w:txbxContent`）里的文字**不在正常段落遍历路径上**，题干/选项被塞进文本框时会**静默丢失**。且文本框的 XML 位置随 Word 版本变化，**没有标准解法**，需要 XPath 全文档扫描。

#### ⑥ 标题检测的"英文门禁"陷阱 ⭐ 直接打中我们的软肋

[docling PR #3961](https://github.com/docling-project/docling/pull/3961)（已 merged）修了一个真实 bug，正文写得很直白：

> 它判断段落是不是标题，**只看样式名里有没有 `"heading"` 这个英文子串**。于是**任何非英文文档的标题层级全部丢失**——"every heading is emitted as body text"。
> **"The level was in the file the whole time."**（层级信息一直在文件里）

**对我们的含义**：**中文 Word 文档的标题样式几乎不可能叫 "Heading"**（是"标题 1"或自定义名）。我们目前**纯靠文本模式**判标题（`第X章` + 长度≤30 + 无句末标点）——一旦文档用样式排版、标题文字又不规律（比如只有"绪论"两个字），就会漏。

**正确做法是三重判定**：

```
① 样式名 / StyleID 命中
② w:outlineLvl ∈ [0,8]    ← OOXML 自己记录的层级，Word 导航窗格读的就是它
   ⚠️ 9 表示正文而非标题，必须排除（否则会出现"幽灵 heading 10"）
③ 文本模式兜底（我们现在的做法）
```

POI 侧可读：`paragraph.getCTP().getPPr().getOutlineLvl()` / `paragraph.getStyleID()`。

#### ⑦ 多栏 PDF：这是 PDFBox 的十年老坑，不是我们的 bug

[PDFBOX-2637](https://issues.apache.org/jira/browse/PDFBOX-2637)（**Open / Unresolved**，建于 2015-01-28，最后更新 2025-02-10）——**挂了 10 年没修**。报告原文（已核实）：

> "I have tried: `setSortByPosition(true)` and **the columns got scrambled**."

**即 `setSortByPosition(true)` 不是多栏问题的解药**——它按坐标排序，对某些文档有效、**对另一些反而把栏序打乱**。

这直接改变我们的策略：**保留它作为默认，但必须有能力检测多栏并回退**（或自研按 x 坐标聚类分栏）。相关地，[PDFBOX-3796](https://issues.apache.org/jira/browse/PDFBOX-3796) 说明 **PDFBox 做表格单元格级还原也不可靠**。

**Java 生态没有 pdfplumber / Camelot 的对应物**：
- [tabula-java](https://github.com/tabulapdf/tabula-java)（2042 star）是唯一成熟的 Java 表格库，但它**强依赖表格有可见线段或对齐的空白列**，且 197 个 open issue。对"表格里装的是段落文本"这个场景**很可能切不出有意义结果**
- [docx4j](https://github.com/plutext/docx4j)（2386 star，**2026-10 仍活跃**）基于 JAXB，**天然保序**，样式/属性访问最完整 → 当 POI 搞不定复杂结构时的**升级路径**
- [Apache Tika](https://github.com/apache/tika)（4084 star）**表格结构会丢失**，只适合格式嗅探

#### ⑧ LLM 兜底现在缺一道"幻觉门" ⚠️ 有定量证据

[MathDoc 基准](https://ar5iv.labs.arxiv.org/html/2601.10104)（3,609 道中文数学题，460 张真实高考卷图像）是目前**唯一直接针对中文数学试卷结构化抽取**的公开基准。关键数据：

| 指标 | 结果 |
|---|---|
| SOTA（Qwen3-VL-30B）题干抽取准确率 | **0.89** |
| 该模型的**拒答召回率** | **0.14**（几乎从不主动拒答） |
| 小模型全页输入时的主动拒答率 | **1.82%** |

论文原文结论：模型**不会报错，而是"forcibly transcribe fragmented content or speculate missing details"（强行转录残缺内容或编造缺失细节）**。

> **对我们的含义**：我们的 LLM 兜底**只校验 JSON 能不能解析，不校验内容对不对**。而"**编造出来的题干/答案是静默污染，比解析失败危险得多**"——因为用户看不出来。

**低成本对策（LaTA 论文的"幻觉门"，可迁移）**：LLM 返回后做结构性校验，不过就**回滚**：

```
✓ 必需标记是否存在（如题干非空、选项字母连续）
✓ 长度在原文的 50%~200%
✓ 特征符号计数（如选项字母数）在原文的 80%~120%
✓ 不含已知幻觉关键词
```

另外论文还有一个**反直觉的警告**：多阶段流水线（MinerU / PaddleOCR-VL）会因为**版面分析阶段的错误级联**而**输给**端到端多模态模型。→ **不要盲目上多阶段版面分析**。

#### ⑨ LLM 三级降级：我们缺第三级

[LaTA 论文](https://ar5iv.labs.arxiv.org/html/2605.05410)的切分是 `正则 → LLM → 整文兜底`，且**每一级失败都返回"整篇作为一个块"+警告标记，绝不返回空**。原文说这套机制让"**全学期部署（200 名学生）无需任何人工分诊**"。

我们现在是两级（规则 → LLM），**缺第三级**：规则和 LLM 都失败时直接报 50001 让用户重传。补一个"整文兜底 + 警告标记"成本很低。

> ⚠️ **诚实说明**：LaTA 的混合理念有完整工程论证和整学期生产验证，但**没有"混合 vs 纯 LLM"的 A/B 定量对比**。所以**不能声称"混合一定更准"**，只能说"确定性优先 + 失败可兜底 + 降级可观测"。

#### ⑩ 输出侧四条确定性护栏 ⭐ 零成本、立刻得到 baseline

[question-bank-studio](https://github.com/jqk512/question-bank-studio) 的做法：解析完成后**强制自检并打标**：

```
缺少答案   题有选项但无答案
选项不足   单选题只有 1 个选项
答案越界   答案字母 > 实际选项数（如答案 D 但只有 A/B/C）   ← 几乎必然是切分错误
题号异常   题号不连续、重复、跳号
```

**为什么这条对你特别重要**：这四条**零成本、零风险**，而且「答案越界」是一个**免费的错误探针**——它能立刻告诉你"哪里切错了"。**这正是你现在缺的 baseline 指标**，而且不需要先建完整的 golden 数据集就能跑起来。

配套还可以抄它的产品设计：
- **检测无文本层的扫描版 PDF**，避免把"扫描件"误判成"空题库"（成本极低）
- **解析失败时优雅降级**成"可检索的文本资料"，而不是硬失败

### 2.6 🔴 已确认的具体 bug：数学题的 LaTeX 反斜杠会炸掉整个分块

这是调研里最有价值的一条，**我在代码里验证过了，是真的**。

**证据链**：

1. AI 抽取要求模型输出 JSON（`response_format=json_object`），解析入口是 [AiQuestionExtractor.java:209](asteria-server/src/main/java/com/asteria/server/ai/AiQuestionExtractor.java#L209) `objectMapper.readTree(json)`
2. [stripToJson()](asteria-server/src/main/java/com/asteria/server/ai/AiQuestionExtractor.java#L229-L252) **只做了两件事**：去 markdown 围栏、截取第一个 `{` 或 `[` 之后的内容。**没有任何转义修复**
3. 全项目 **grep 确认没有任何自定义 Jackson 配置**（无 `JsonReadFeature`、无 `configure(...)`），用的是 Spring Boot 默认 ObjectMapper → **严格按 JSON 规范处理转义**

**故障场景**：数学/物理题库的题干含 LaTeX，模型忠实输出：

```json
{"stem": "求 \frac{1}{2} + \frac{1}{3} 的值"}
```

JSON 规范里 `\f` 是**换页符**（合法转义），所以 Jackson **不会报错**，而是把 `\frac` 解析成 **换页符 + "rac"** → 题干**静默损坏**成 `求 <FF>rac{1}{2} + <FF>rac{1}{3} 的值`。

而 `\alpha`、`\beta`、`\times` 这类是**非法转义**，Jackson 直接抛异常 → `callOnce` 整块失败 → 重试一次仍失败 → **整个分块抛 50001，整批导入失败**。

**两种情况都很糟**：一种是静默污染（用户看不出来），一种是整批失败。

**修复方向**（LaTA 论文里叫 "LaTeX-aware sanitizer"）：在 `stripToJson` 之后、`readTree` 之前加一层转义修复——

```
把未转义的单反斜杠 \ 转成 \\，但要【避开】真正的 JSON 转义：
  \n  \t  \r  \b  \f  \"  \\  \/  \uXXXX   ← 这些保持原样
  其余（\frac  \alpha  \begin ...）        ← 补成 \\frac
```

⚠️ 关键细节：`\f` 本身是合法转义，所以**不能简单地"所有 `\` 都翻倍"**，必须做合法性判定。这也正是这条 bug 隐蔽的原因。

**这条值得单独写进简历**：它属于"**LLM 输出不可信，必须做防御性解析**"这一类工程问题，比"实现了 AI 解析"有含量得多。

## 三、线 3 · AI 解析部分优化（你提的重点）

### 3.1 现状的四个硬伤（都已在代码里证实）

| # | 问题 | 证据 | 代价 |
|---|---|---|---|
| A1 | **一题一次请求，完全串行** | [BanksServiceImpl.java:329-357](asteria-server/src/main/java/com/asteria/server/Services/impl/BanksServiceImpl.java#L329-L357) `for (question : questions) { enrich(...) }`，`QuestionAiEnricher.enrich` 内部一次 `chatModel.call` | 500 题的库 = **500 次 HTTP + 500 次完整系统提示词**，慢且贵到不可用 |
| A2 | **`getFormat()` 每个请求都拼** | [QuestionAiEnricher.java:63](asteria-server/src/main/java/com/asteria/server/ai/QuestionAiEnricher.java#L63) `buildUserPrompt(...) + "\n" + converter.getFormat()` | JSON schema 说明**每次都重发**，白烧 token（schema 是固定的） |
| A3 | **没有断点续跑** | 失败只 `failed++` 记日志（[:341-345](asteria-server/src/main/java/com/asteria/server/Services/impl/BanksServiceImpl.java#L341-L345)），DB 无任何标记 | 500 题跑到第 400 题崩了 → **重跑要重新付前 400 题的钱** |
| A4 | **AI 答案覆盖原答案，且不可追溯** | [:333-338](asteria-server/src/main/java/com/asteria/server/Services/impl/BanksServiceImpl.java#L333-L338) 直接 `updateById(patch)` 写回 `analysis` / `answer` | `question` 表**无法区分"文件里原本就有"和"AI 生成的"**；原答案被覆盖后无法回滚、无法人工复核 |

> A4 是**数据治理问题**，不只是效率问题。将来你想做「AI 解析人工确认」，会发现原始数据已经没了。

### 3.2 改造方向：**批量 + 可续跑 + 可追溯**

```
现在：  500 题 → 500 次请求（串行，每 5 题落一次进度）
                 总耗时 ≈ 500 × 3s = 25 分钟
                 系统提示词重复 500 次

改后：  500 题 → 分片（每片 10~20 题）→ 每片 1~2 次请求
                 批次内并发（4~8），带退避与限流
                 总耗时 ≈ (500/15) × 4s / 6并发 ≈ 22 秒   【约 60~70 倍】
                 系统提示词 + JSON schema 固定 → 可命中服务商 prompt 缓存

        同时：每片处理完立即落库 + 标记状态 → 崩了从那片继续
```

> ⚠️ **但调研纠正了一个我原先没考虑的点：批量和前缀缓存是有张力的。**
>
> DeepSeek / OpenAI / Qwen / Kimi **全部是前缀缓存**，且 DeepSeek 官方明确要求「**identical prefixes starting from the 0th token**」——中间部分相同**不算命中**。而你现在「一题一次调用、system prompt 完全不变」的循环，**恰好是缓存命中的最优形态**。
>
> 所以批量化的收益要重新算：**它省的是系统提示词 + JSON schema 的重复发送，不是省"缓存"**。两种方案的取舍是：
>
> | 方案 | 请求数 | Token | 延迟 | 缓存 |
> |---|---|---|---|---|
> | 逐题并发（现结构 + 虚拟线程） | 500 | 高（schema 重复 500 次） | 低 | ✅ 全命中 |
> | 批量 15 题/请求 | ~34 | 低 | 更低 | ⚠️ 片内共享前缀，仍可命中 |
>
> **务实结论**：先做「虚拟线程并发 + 前缀固定」，这已经能拿到大部分收益且**不改变现有单题语义**；批量再作为第二步，且**批大小要实测**（调研给的起点是 8~10 题/请求）。不要一上来就批量。

### 3.3 具体改造点

| # | 改造 | 做法 | 收益 |
|---|---|---|---|
| M0 | **虚拟线程并发**（先做这个） | JDK 21 的 `Executors.newVirtualThreadPerTaskExecutor()` + `Semaphore(N)` 限流。JEP 444 官方 javadoc 原文：**"do not be tempted to pool virtual threads in order to limit concurrency. Instead use constructs specifically designed for that purpose, such as semaphores"** | 不改语义就能把 25 分钟压到分钟级 |
| M1 | **批量补全**（第二步） | 一次请求塞 N 题（起步 8~10，要实测），返回 JSON 数组；**必须校验返回条数 == 请求条数**（「Lost in the Middle」arXiv:2307.03172 证明长上下文中部信息利用率下降） | 请求数与 schema 重复量 ↓ 90%+ |
| M2 | **提示词前缀固定** | 系统提示词 + JSON schema 放在**消息最前面且字节级固定**——⚠️ **别把题目 ID 拼进 system prompt**（否则前缀变化，缓存全失效） | 命中前缀缓存（DeepSeek 命中价与未命中价差约 50 倍） |
| M2.5 | **记录缓存命中率** | 记录 `prompt_cache_hit_tokens`，让缓存收益可见 | 简历上能给出"缓存命中率 X%" |
| M3 | **退避 + 限流** | 指数退避 + 429 专门处理 + 单批超时 | 既快又不触发限流 |
| M4 | **断点续跑** | 给 `question` 加 `ai_status`(PENDING/RUNNING/DONE/FAILED) + `ai_error`；**乐观抢占**：`UPDATE ... WHERE ai_status='PENDING'` | 崩溃后重跑只付增量 |
| M4.5 | **`prompt_hash` 唯一索引** | 内容哈希 = hash(题目文本 + prompt 版本)；**prompt 改版自动全部失效重算** | 同一输入永不重复付费 |
| ⚠️ | **绝不要把 LLM 调用放进数据库事务** | 顺序必须是：乐观抢占 → **事务外调 LLM** → 结果与状态一次写回。核心认知：**LLM 调用不是幂等的**（重试真的再花一次钱），所以接受 at-least-once、让**写入**幂等 | 避免长事务锁表 |
| M5 | **可追溯：加 `answer_source`** | 记录答案来源：`FILE`（文件里抽的）/ `AI`（模型解的）/ `MANUAL`（人工改的）；AI 写回时**保留原值** | 支持人工复核、支持回滚 |
| M6 | **答案一致性自检** | 模型给的答案与文件答案冲突时**不覆盖**，只记录冲突供人工看 | 防止 AI 悄悄改错标准答案 |
| M7 | **失败原因可见** | 现在失败只进日志（注释自认"写进去用户也看不见"） | 把失败题数和原因回传给前端 |
| M8 | **解析质量闸门** ⭐ | 见下方「最值得写的一条」 | 简历含金量最高 |

### 3.4 关于「解析质量」——这一条最值得写进简历 ⭐

调研找到一条**直接命中你场景**的硬证据。

[Turpin et al., NeurIPS 2023](https://arxiv.org/abs/2305.04388) 原文：

> **"When we bias models toward incorrect answers, they frequently generate CoT explanations rationalizing those answers."**
> 这类解释 "**plausible yet misleading**" —— 看起来合理，实则误导。

**你的系统正是「给模型一道题，让它产出解析，然后直接把解析展示给学习者」。** 而学习者（尤其是学生）**没有能力识别一个自信的错误解析**。

> 这也解释了为什么 MathDoc 的拒答召回率只有 0.14——**模型不会说"我不确定"，它会编一个像样的理由。**

**最低成本的防线（按成本排序）**：

| 手段 | 做法 | 额外成本 |
|---|---|---|
| **答案一致性检查** | 把「题干 + 选项 + 正确答案 + AI 解析」再喂回去，问「这段解析是否支持该答案」 | 1 次调用 |
| **UI 明示** | 解析上打「AI 生成」标识，与"文件自带解析"在视觉上区分 | 0 |
| **一键报错** | 用户能标记"这个解析不对"，落库供你回看 | 0 |
| **弃权机制** | prompt 里给出「无法确定时返回 `analysis: null`」 | 0 |

**为什么这条最值得写进简历**：调研的原话是——**「多数人只谈『怎么生成』，能谈『怎么知道生成的是对的』的极少」**。这正是"AI 应用开发"和"调了个 API"的分界线。

### 3.5 各家结构化输出能力有真实差异（要留降级矩阵）

调研核实的能力矩阵（**这决定了你不能假设所有 OpenAI 兼容端点行为一致**）：

| 厂商 | `json_object` | `json_schema` + strict |
|---|---|---|
| DeepSeek | ✅ | ❌ 文档未提供 |
| Qwen 百炼 | ✅ | ✅ 但**仅部分模型** |
| Kimi | ✅ | ✅ |
| Zhipu/GLM | ✅ | ❌ 只有 `json_object`（schema 靠 prompt 贴 + 客户端校验） |

**三个具体的坑**：

1. DeepSeek 官方承认「the API **may occasionally return empty content**」→ 必须处理空响应
2. **`max_tokens` 的建议厂商之间是矛盾的**：Qwen 说「Do not set max_tokens」（会截断 JSON），DeepSeek 说「Set the `max_tokens` parameter reasonably」
3. Qwen 明确「JSON Object 模式**不保证键名和字段类型稳定**」

→ **结论：客户端永远做 schema 校验 + 重试，不要信任服务端的约束。** 你现在的 `AiQuestionExtractor` 逐题校验思路是对的，扩展成批量时要保持。

### 3.6 ❌ 明确判定为「过度工程」的（这部分和正面建议同等重要）

调研把几条**看起来很像正经解法、但对本项目是浪费**的路排除了：

| 不做 | 依据 |
|---|---|
| **Spring Batch** | 官方定位 enterprise / 每天数十亿事务，需要一整套 `BATCH_*` 元数据表；且官方声明 XML namespace 在 6.0 弃用、7.0 移除。**一张 `ai_status` 列就够的事** |
| **改写 `ORDER BY RAND()`** | 它确实是 O(n log n) 全表扫 + filesort，但 `ROW_NUMBER() OVER (ORDER BY RAND())` **不改变本质**；随机 id 区间法有「id 有空洞时严重偏斜」的缺陷。**你现在的「全量取 id + Fisher-Yates」在几万题以内是合理的，真正该做的只有加 cap** |
| **CAT / IRT 自适应测验** | 选题算法不难，难的是每道题需要 IRT 参数（a/b/c），要预测试 + 大样本标定 → **单用户题库永远达不到** |
| **Idempotency-Key 头** | IETF 草案 [draft-ietf-httpapi-idempotency-key-header-07](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) **已 Expired & archived，从未成为 RFC** |
| **constrained decoding**（outlines / XGrammar / GBNF / vLLM） | **全部需要自托管推理**，托管 API 不暴露 logits 钩子 → 架构上就不通 |
| **GPTCache / LiteLLM** | 都是 Python 项目。用一张 `prompt_hash` 精确缓存表替代，还避免了语义缓存的误命中风险 |

### 3.7 可借鉴的参考（已检索）

## 四、线 4 · 随机答题优化 —— ❌ **已决定不做，保持原样**

> **决定（2026-10-03，用户拍板）**：随机抽题**保持现状**，不做加权/分层/可复现那套改造。
> 理由：当前实现（全量取 id + `Collections.shuffle`）在几千题规模下完全够用，
> 加策略是**过度设计** —— 复杂度上去了，用户能感知到的差别很小。
>
> 本节内容**保留作为资料**（万一以后题库到几万题、或者真需要"模拟考试可复现"再回来看），
> 但**不再作为待办**。下面「亮点池」和「推进顺序」里的相关条目也已标注为不做。

### 4.1 现状的三个问题（记录备查，不作为待办）

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| R1 | **"随机"只是把整库打乱** | [PracticeServiceImpl.java:545-551](asteria-server/src/main/java/com/asteria/server/Services/impl/PracticeServiceImpl.java#L545-L551) 全量查 id + `Collections.shuffle` | 5000 题的库抽 10 题，也要**把 5000 个 id 全查出来、全建会话清单**（N 行 INSERT）；无题数上限 |
| R2 | **无策略：不会的题和会的题一样概率** | 均匀随机 | 刷了 100 题，60 题是已经会了的，浪费时间 |
| R3 | **随机不可复现** | `Collections.shuffle(ids)` 用默认随机源，无 seed | 出过的顺序无法重放（做"模拟考试"就需要可复现） |

> 说明：这三条**不是 bug，是"可以更好"**。项目定位是本地个人使用，
> 均匀随机已经满足需求；等到真觉得"抽到的题太简单"或者"想做模拟考试"再动。

### 4.2 改造方向（如果将来要做）：**从"乱序"升级成"可配置的抽题策略"**

这是最容易做出**简历亮点**的一条线——因为它对应真实产品需求，而且算法复杂度可以量化。

```
抽题策略（可组合）：

① 加权随机（Weighted Sampling）
   权重 = f(错误率, 最近是否错过, 是否已攻克, 距上次练习天数)
   例： weight = 1 + 3×wrongRate + 2×(resolved==0) + recency
   实现：A-Res 加权蓄水池抽样（一次遍历、O(k log k)），或按权重区间做前缀和 + 二分

② 分层抽样（Stratified Sampling）
   按章节 / 题型分层，每层按比例分配名额 → 保证一次练习覆盖每一章
   解决"随机抽 20 题里有 15 题都来自第 3 章"

③ 可复现（Seeded Shuffle）
   practice_session 加 seed；用 new Random(seed) / SplittableRandom 洗牌
   → 同一 seed + 同一题库 = 同一套题同一顺序（模拟考试、错题重做对照）
   ⚠️ 必须自己写 Fisher-Yates，不要用 Collections.shuffle（原因见下）

④ 只抽 N 题（不再全量）
   直接 SQL 抽样或内存蓄水池，避免把整库 id 拉出来
```

### 4.3 配套：**每题的掌握度指标**

有个**反直觉的调研结论值得单独说**——关于"可复现随机"：

> **`Collections.shuffle` 的可复现性保障比 `Random` 弱得多。**
>
> - `java.util.Random` 的 javadoc 有**规范级强保证**："Java implementations **must** use all the algorithms shown here for the class Random, **for the sake of absolute portability** of Java code" → 同种子跨 JDK 实现结果一致
> - 但 `Collections` 类的 javadoc 明确声明实现描述只是 "**implementation notes, rather than parts of the specification**"，且 "**Implementors should feel free to substitute other algorithms**" → **shuffle 的内部算法不受规范保护**，跨 JDK 大版本升级后不保证同一排列
> - 无参 `Collections.shuffle(List)` 用的"default source of randomness"**更不在规范内**

**所以要长期可复现（比如"同一份模拟卷三个月后还能重放"），必须自己写 Fisher-Yates 循环 + `new Random(seed)`**，不能依赖 `Collections.shuffle` 的内部实现。这是个很小但很"懂行"的细节，写进注释里就是亮点。

没有分母就没有"错误率"。建议在 `question` 上维护两个累计计数器（而不是每次 `COUNT(*)`）：

| 字段 | 含义 | 用途 |
|---|---|---|
| `practice_count` | 被作答总次数 | 分母 |
| `correct_count` | 答对总次数 | 正确率 = correct/practice |

有了它，加权抽题、掌握度展示、薄弱章节定位全都能做。

### 4.4 关于"间隔重复"（要不要上 FSRS）

我查了一下，Java 这边**确实有现成的 FSRS 实现**：

- [open-spaced-repetition/java-fsrs](https://github.com/open-spaced-repetition/java-fsrs) —— 官方组织的 Java 库
- [haoxstrong/java-fsrs](https://github.com/haoxstrong/java-fsrs) —— JNI 调 Rust 实现，性能更好

**我的建议：先不上，但预留接口。**

理由：
- FSRS 需要**评分数据**（每次复习的 1~4 档回忆难度），你现在只有"对/错"二值 → 数据不够，硬上就是**伪 FSRS**，简历上反而容易被问穿
- 改用**简单的"错题优先 + 遗忘曲线加权"**，就能拿到 80% 的收益，而且能讲清楚
- 如果真要上，做成**可插拔的策略接口**（`QuestionSampler` 接口 + 多个实现：均匀 / 加权 / FSRS），这本身就是很好的设计亮点，且不阻塞

> **简历写法**：不要写"实现了 FSRS"（会被追问细节），写「抽象出可插拔抽题策略，实现均匀/加权/分层三种采样算法，错误率高与待攻克的题目被抽中概率提升 X 倍」——这是**你真做过的**，且经得起追问。

## 五、线 5 · 数据库层面（你问的）

我把 12 张表的 DDL 全过了一遍。**整体设计是合理的**（唯一键、级联策略、冗余列都有明确理由），但有 **6 处可优化**，其中前 3 处有明确的性能收益：

### 5.1 性能类（有量化收益）

| # | 问题 | 位置 | 优化 | 收益 |
|---|---|---|---|---|
| **DB1** | 每次提交答案都 `COUNT(*)` 重算会话计数 | `practice_record` 上只有 `uk(session_id,question_id)`，**没有 `(session_id, is_correct)` 索引** | ① 加索引 `idx_pr_session_correct(session_id, is_correct)` ② 或（更好）改成**增量更新** `answered_count + 1` | 单会话 O(N²) → O(1)，500 题会话少扫 12.5 万行 |
| **DB2** | **AI 补全进度全在内存** | `importTasks` 是 `ConcurrentHashMap`，重启即丢 | 新建 `enrich_task` 表（task_id / bank_id / status / progress / 失败题数 / 错误摘要） | 重启可续跑、失败可见（配合线 3 的 M4/M7） |
| **DB3** | 聊天会话列表全表加载 + 内存排序 | `chat_session` 只有 `idx_cs_updated`，但代码是 `selectList(null)` 后内存排序 | 改 `ORDER BY updated_at DESC LIMIT` | 会话多了不再全表扫 |

### 5.2 数据质量类（这才是真正的亮点）

| # | 问题 | 位置 | 优化 | 为什么是亮点 |
|---|---|---|---|---|
| **DB4** | **无法区分答案来源** | `question.answer` 只有一个字段，文件抽的和 AI 解的混在一起 | 加 `answer_source`（FILE/AI/MANUAL）+ `ai_generated_at` | 「数据血缘」是正经工程概念，简历上很吃分 |
| **DB5** | **AI 补全状态无处记录** | 失败只进日志 | 加 `ai_status` + `ai_error` + `prompt_hash`（唯一索引，prompt 改版自动失效重算） | 让"重试失败题"成为可能，且同一输入永不重复付费 |
| **DB6** | **导入解析结果不可追溯** | 切题出错只能重传文件 | 新表 `import_question_raw`（task_id, seq, raw_json, suspicious, 最终是否入库） | �  用户可在界面上核对"AI 抽的这道题对不对"→ 可做**人工校对界面**，这是很亮的功能 |

| 项 | 原因 |

| 把 JSON 列拆成子表 | 当前访问模式不适合拆（见 5.3） |

## 十、一句话总结

> **别做"功能更多"，要做"更可信、更可测、更可解释"。**
>
> 主线收敛成两条（随机答题那条已决定不做）：
> **识别率有评测数据** · **AI 解析有并发提速 + 失败可解释**。
> 加上架构图与「设计亮点」章节，这个仓库就从"个人练习项目"变成"有工程度的作品"。
