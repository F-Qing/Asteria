# 第 1 章：完整代码（可运行的真实版本）

先把完整方法贴出来（这就是项目里的真实代码，我加了行号注释）：

```java
private void aiEnrich(String taskId, Long bankId, AiRequestConfig aiConfig) {

    // ① 从数据库捞"还没解析成功"的题
    List<Question> questions = questionMapper.selectList(
            Wrappers.<Question>lambdaQuery()
                    .eq(Question::getBankId, bankId)
                    .ne(Question::getAiStatus, AiStatus.DONE.name()));
    int total = questions.size();
    if (total == 0) {
        log.info("AI 解析：没有需要处理的题，跳过。taskId={}, bankId={}", taskId, bankId);
        return;
    }
    log.info("AI 解析开始：taskId={}, bankId={}, 待处理{}题, 并发度{}", taskId, bankId, total, AI_CONCURRENCY);

    updateTask(taskId, ImportStatus.AI_PROCESSING.name(), 0, total, bankId);

    // ② 两个计数器 + 一把锁  ← 会在多线程里被同时读写，必须用特殊类型
    AtomicInteger done = new AtomicInteger();      // 已处理题数
    AtomicInteger failed = new AtomicInteger();    // 失败题数
    Object progressLock = new Object();            // 专门用来"排队"的对象

    // ③ 创建执行器（括号里的写法会在代码块结束时自动关闭）
    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {

        // ④ 创建信号量：最多 6 个任务同时进行
        Semaphore limiter = new Semaphore(AI_CONCURRENCY);

        // ⑤ 把每道题都提交给执行器
        for (Question question : questions) {
            executor.submit(() -> {                // ← 这个 {} 里的代码会被"另一个线程"执行

                // 5.1 拿名额（拿不到就在这里等）
                try {
                    limiter.acquire();
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                    log.warn("AI 解析被中断，放弃剩余任务：questionId={}", question.getId());
                    return;                        // 放弃这道题
                }

                // 5.2 真正干活
                try {
                    enrichOne(question, aiConfig);
                } catch (Exception e) {
                    failed.incrementAndGet();
                    markEnrichFailed(question, aiConfig, e);
                } finally {
                    limiter.release();             // 无论成功失败都要还名额
                }

                // 5.3 更新进度
                int finished = done.incrementAndGet();
                int progress = (int) (finished * 100L / total);
                synchronized (progressLock) {      // 这一段同一时间只允许一个线程进
                    updateTask(taskId, ImportStatus.AI_PROCESSING.name(), progress, total, bankId);
                    if (finished % 5 == 0 || finished == total) {
                        bankImportMapper.updateById(BankImport.builder()
                                .taskId(taskId)
                                .progress(progress)
                                .build());
                    }
                }
            });
        }
    } catch (Exception e) {
        log.error("AI 解析批处理异常：taskId={}", taskId, e);
    }

    int okCount = total - failed.get();
    log.info("AI 解析结束：taskId={}, 成功{}题, 失败{}题", taskId, okCount, failed.get());
}
```

**先建立起整体印象**：

```
第 ① 步  准备工作（单线程做的，和以前一样）
第 ② 步  准备"安全的计数器"
第 ③ 步  开一个"工人池"
第 ④ 步  准备"车位牌子"
第 ⑤ 步  for 循环：把 500 道题逐个丢进去
            └─ 每个任务内部：拿车位 → 干活 → 还车位 → 报进度
```

# 第 2 章：逐块拆解

## 2.1 `ExecutorService`：管工人的"包工头"

### 语法

```java
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
```

拆开看这几个词：

| 词 | 意思 |
|---|---|
| `ExecutorService` | 一个**接口**（interface），意思是"能执行任务的执行器" |
| `Executors` | 一个**工具类**，专门用来创建各种执行器（注意结尾有 **s**） |
| `newVirtualThreadPerTaskExecutor()` | 方法名直译：**"每个任务一个新虚拟线程的执行器"** |

### 为什么名字这么长

这是个**刻意起得啰嗦**的方法名。Java 里类似的还有：

```java
Executors.newFixedThreadPool(6)              // 固定 6 个线程（传统线程，会复用）
Executors.newCachedThreadPool()              // 需要多少开多少，空闲回收（传统线程）
Executors.newSingleThreadExecutor()          // 只有 1 个线程（排队执行）
Executors.newVirtualThreadPerTaskExecutor()  // ★ 每任务一个虚拟线程（我们用的）
```

**为什么选最后一个**：

| 方式 | 问题 |
|---|---|
| `newFixedThreadPool(6)` | 只有 6 个工人。第 7 个任务要**排队等工人空出来**。而工人"等网络"时被占着，白等 |
| `newCachedThreadPool()` | 会开很多传统线程，每个约 1MB 内存，500 个就是 500MB |
| `newVirtualThreadPerTaskExecutor()` | 每任务开一个**虚拟线程**，等网络时自动让出底层资源，几乎不花钱 |

> 💡 **一句话**：`newFixedThreadPool` 是"6 个员工干 500 件事"，`newVirtualThreadPerTaskExecutor` 是"500 个临时工干 500 件事，但临时工不要工位"。

### 那 6 个并发限制怎么办

**关键理解**：这个执行器**不限制并发**。你提交 500 个任务，它就开 500 个虚拟线程。

**限制并发是信号量干的活**（第 4 步）。这两件事**必须分开**：

```
执行器负责：怎么执行（用虚拟线程）
信号量负责：同时允许多少个（6 个）
```

## 2.2 `try (...)`：等所有人下班的写法

### 语法

```java
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // 干活
}   // ← 这个右括号，会等所有任务跑完才继续
```

这种写法叫 **try-with-resources**（带资源的 try）。

**普通 try 是这样**：

```java
try {
    干活();
} catch (Exception e) {
    处理错误();
}
```

**try-with-resources 是这样**：`try` 后面多了一对括号，里面**声明并初始化**一个对象。

```java
try (在这里声明对象) {
    干活();
}
```

### 它到底做了什么

**规则**：括号里的对象，如果是"可关闭的"（实现了 `AutoCloseable` 接口），那么
**不管代码块正常结束还是抛异常，Java 都会自动调用它的 `close()` 方法**。

展开成"老式写法"就是：

```java
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
try {
    干活();
} finally {
    executor.close();     // ← 编译器自动帮你加上的
}
```

### 为什么必须写这个括号

`ExecutorService.close()` 的语义是：**停止接受新任务，并且等已经提交的任务全部跑完**。

**如果不写括号会发生什么**：

```java
// ❌ 错误写法
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
for (Question q : questions) {
    executor.submit(() -> 处理(q));     // 任务提交了，但可能还没开始跑
}
log.info("AI 解析结束");                 // ← 这里会立刻执行！很多题还没处理完
// 方法返回了，但后台还有几百个任务在跑 → 进度乱了、状态不对
```

**用了括号之后**：

```java
try (ExecutorService executor = ...) {
    for (Question q : questions) {
        executor.submit(() -> 处理(q));
    }
}                                        // ← 卡在这里，直到 500 个任务全部结束
log.info("AI 解析结束");                  // ← 这时候才是真的结束了
```

> 💡 **这是初学者最容易踩的坑**：以为 `submit` 是"立刻执行完"，其实 `submit` 只是"交给它去做"，
> 方法会立刻返回。**必须用 try-with-resources 等它们。**

### `close()` 会自动等，那会不会卡住

会等，但**这是我们要的**。`aiEnrich` 本身就跑在后台线程里（第 284 行那个 `new Thread`），
所以它等多久都不影响用户 —— 用户在浏览器上看到的是**进度条在涨**。

## 2.3 `submit(() -> {...})`：lambda 表达式

### 语法

```java
executor.submit(() -> {
    // 这里写要被"另一个线程"执行的代码
});
```

那个 `() -> { ... }` 叫 **lambda 表达式**。

### 拆开看

```java
() -> { 代码 }
│    │   └── 方法体（要干的事）
│    └────── 箭头，读作"变成"或"去执行"
└─────────── 参数列表（空的，表示"不需要参数"）
```

**对比一下"老式写法"**（Java 8 之前必须这么写）：

```java
// 老式：造一个匿名内部类
executor.submit(new Runnable() {
    @Override
    public void run() {
        处理这道题();
    }
});

// Lambda：等价，但短得多
executor.submit(() -> 处理这道题());
```

**Lambda 能简写的原理**：`submit` 方法要的参数类型是 `Runnable`，而 `Runnable` 只有一个方法 `run()`。
Java 一看"这个接口只有一个方法"，就知道你写的 lambda 一定是给 `run()` 用的，所以：

- 不用写 `new Runnable()`
- 不用写 `@Override public void run()`
- 参数列表空就写 `()`

> 💡 **术语**：这种"只有一个抽象方法的接口"叫**函数式接口**（functional interface）。
> Lambda 只能用在函数式接口上。

### 为什么这里能直接用到外面的变量

看这段：

```java
for (Question question : questions) {
    executor.submit(() -> {
        enrichOne(question, aiConfig);   // ← question 和 aiConfig 都是外面的变量
    });
}
```

**lambda 里能直接用外面的变量**，这叫**闭包**（closure）。但有两条规矩：

| 规矩 | 说明 |
|---|---|
| 变量必须是 **final 或"事实上的 final"** | 意思是**声明后不能再赋值** |
| 不能修改它 | 只能读 |

**为什么有这样的限制**：`question` 是循环变量，每圈都变。如果允许 lambda 里改它，就会
出现"哪个线程看到的是哪个值"的混乱。所以 Java 干脆禁止修改。

**那如果我们真的需要在 lambda 里计数怎么办**？——这就是下一节 `AtomicInteger` 存在的原因。

```java
// ❌ 编译不过：done 在后面被 +1 了，不是"事实上的 final"
int done = 0;
executor.submit(() -> { done++; });   

// ✅ 用 AtomicInteger
AtomicInteger done = new AtomicInteger();
executor.submit(() -> { done.incrementAndGet(); });   // 调方法，不是重新赋值，所以合法
```

## 2.4 `Semaphore`：停车场车位

### 语法

```java
Semaphore limiter = new Semaphore(AI_CONCURRENCY);   // 6 个车位

limiter.acquire();    // 拿一个车位（没有空的就等着）
limiter.release();    // 还一个车位
```

### 为什么叫 Semaphore

这个词来自交通信号（铁路的信号灯）。在编程里它就是一个**带计数的许可证管理器**：

```
new Semaphore(6)  →  发了 6 张许可证
acquire()         →  拿走一张（一张都没有了？那就在这儿等别人还）
release()         →  还回一张（有人还了，等着的那个就能拿走）
```

> **打个比方**：停车场门口牌子写"剩余车位 6"。
> 车来了看一眼：有位置就进，牌子减 1；牌子是 0 就在门口排队；有车开走牌子加 1，排队的第一辆进。
> **注意"牌子"本身不限制停车场能容纳多少车（那是执行器的事），它只限制"同时进去几辆"。**

### 完整用法（三行缺一不可）

```java
try {
    limiter.acquire();      // ① 拿车位
    try {
        干活();              // ② 干活
    } finally {
        limiter.release();  // ③ 还车位（必须在 finally）
    }
} catch (InterruptedException e) {
    处理中断();
}
```

**为什么 `release()` 一定要放 `finally`**：

```java
// ❌ 危险写法
limiter.acquire();
干活();              // ← 如果这里抛异常
limiter.release();   // ← 这行就永远不执行了，车位永久少一个

// 跑几次之后：车位从 6 → 5 → 4 → ... → 0
// 结果：所有任务都在门口干等，程序看起来"卡死"了
```

这种现象叫**信号量泄漏**（semaphore leak），是并发编程的经典 bug。

### 为什么不用固定 6 个线程的池

你可能会想："既然要限制成 6 个，那我为什么不直接用 `newFixedThreadPool(6)`？"

**因为那两件事是独立的需求**：

| 需求 | 用什么解决 |
|---|---|
| 用什么方式执行（虚拟线程） | `ExecutorService` |
| 同时允许几个（6 个） | `Semaphore` |

如果混在一起（用固定池），你就被绑死在"必须有 6 个工人"上，失去了虚拟线程的好处。

而 Java 官方文档（JEP 444）里专门写了一句话：

> **"不要试图用线程池来限制虚拟线程的并发，而是用信号量。"**

### 为什么是 6 这个数字

代码注释里写了原因，核心是**数据库连接池**：

```java
private static final int AI_CONCURRENCY = 6;
```

```
每道题处理完 → 要写回数据库 → 要从连接池借一条连接
HikariCP（默认的连接池）默认给 10 条连接
但除了写题目，进度、任务状态也要写库 → 留余量 → 取 6
```

**如果并发开 50 会怎样**：

```
50 个线程想写数据库 → 只有 10 条连接 → 40 个在排队
结果：并发度实际只有 10，多出来的 40 个纯属白开
```

## 2.5 `AtomicInteger`：不会数错的计数器

### 先看问题：为什么普通 `int` 不行

假设两个线程同时给 `count` 加 1：

```java
int count = 0;
count++;    // 看起来是一行，其实是三步
```

`count++` 在底层是**三步操作**：

```
① 读：把 count 的值读到寄存器     （假设读到 0）
② 加：寄存器 + 1                  （变成 1）
③ 写：把寄存器写回 count          （count = 1）
```

**两个线程同时做会怎样**：

```
时刻   线程A                线程B              count 的值
────────────────────────────────────────────────────────
 t1    读到 0                                  0
 t2                         读到 0              0     ← B 也读到了 0！
 t3    算出 1                                  0
 t4                         算出 1              0
 t5    写入 1                                  1
 t6                         写入 1              1     ← 写了个寂寞，还是 1
```

**两个线程各加了一次，结果只加了 1。** 这叫**竞态条件**（race condition）。

### `AtomicInteger` 怎么解决

```java
AtomicInteger count = new AtomicInteger(0);

count.incrementAndGet();   // 加 1 并返回新值（原子操作）
count.get();               // 读当前值
count.addAndGet(5);        // 加 5
```

**"原子"（atomic）的意思**：这个操作**不可分割**，要么整个做完，要么完全没做，
中间**不会被别的线程插进来**。

底层靠的是 CPU 提供的**比较并交换**（CAS, Compare-And-Swap）指令：

```
CAS(期望值, 新值)：
  "如果当前值等于'期望值'，就把它改成'新值'；否则什么都不做并告诉我失败了"
  → 这三步由 CPU 一条指令完成，中间不可能被打断
```

### 我们代码里怎么用的

```java
AtomicInteger done = new AtomicInteger();      // 默认初始值 0
AtomicInteger failed = new AtomicInteger();

// 在多个线程里被调用：
int finished = done.incrementAndGet();          // 加 1，并把加完的值拿到手
failed.incrementAndGet();

// 方法结束时读：
int okCount = total - failed.get();             // .get() 读取当前值
```

**注意 `incrementAndGet()` 返回的是"加完之后的值"**。所以：

```java
int finished = done.incrementAndGet();   // 第 1 个完成的线程拿到 1，第 2 个拿到 2……
int progress = (int) (finished * 100L / total);   // 直接能算百分比
```

> 💡 **为什么不用 `synchronized` 包住 `count++`**：也能解决，但那样会**让所有线程排队加 1**，
> 加个数字都要排队，性能差。`AtomicInteger` 不需要锁，靠 CPU 指令完成。

## 2.6 `synchronized`：排队进小房间

### 语法

```java
Object lock = new Object();       // 先准备一把"锁"

synchronized (lock) {             // 同一时间只有一个线程能进这个块
    // 这里面的代码是串行的
}
```

**读法**："用 lock 这把锁，把下面这段代码锁住。"

### 为什么需要它

看我们的进度更新代码：

```java
int progress = (int) (finished * 100L / total);
updateTask(taskId, ..., progress, ...);         // 改内存里的任务快照
if (finished % 5 == 0) {
    bankImportMapper.updateById(...);            // 写数据库
}
```

**问题**：多个线程会同时执行这段。而这段里的操作**不是原子**的：

```
线程A：读到进度是 20
线程B：读到进度是 21
线程A：把进度写成 20
线程B：把进度写成 21
→ 最终是 21，看起来没问题？
```

但如果顺序反过来：

```
线程A：读到 20       线程B：读到 21
线程B：写入 21
线程A：写入 20       ← 进度"倒退"了！
→ 用户看到进度条从 21% 跳回 20%
```

**更麻烦的是数据库**：多个线程同时 `UPDATE` 同一行任务记录，可能互相覆盖成不一致的状态。

### `synchronized` 怎么解决

```java
synchronized (progressLock) {
    updateTask(...);        // 这一段同一时间只有一个线程在执行
    if (...) { 写数据库(); }
}
```

**进入这个块之前要拿到 `progressLock` 这把锁**，拿不到就在门外等。因为只有一个线程能持有锁，
所以块里的代码**变成串行的**。

### 那把锁是什么

```java
Object progressLock = new Object();
```

**就是一个普通的空对象**，唯一作用是"当锁用"。

**为什么不用别的对象当锁**：
- 用 `this`（当前对象）会**影响到别的地方**（别人也可能 synchronized(this)）
- 用 `String` 常量可能被 JVM 复用（不同地方拿到同一个对象）
- **专门 `new Object()` 最安全**：只有我们知道它，不可能被别人锁

> 💡 **Java 里任何对象都能当锁**，这不是什么特殊类型。`synchronized` 就是"给对象加个占用标记"。

### 为什么只锁这一小段

`enrichOne(question, aiConfig)`（调 AI 那 3 秒）**没有**被锁住 —— 这是刻意的：

```java
enrichOne(question, aiConfig);      // ← 不锁！6 个线程可以同时调 AI

synchronized (progressLock) {       // ← 只锁"更新进度"这几十微秒
    更新进度();
}
```

**如果把调 AI 也锁起来**，那就变成**串行了**，并发改造白做。

**原则**：**锁的范围越小越好**，只锁必须串行的部分。

# 第 3 章：执行顺序走一遍

假设有 **3 道题**，并发度 **2**。真实执行时间轴大概是这样：

```
时间 →  ─────────────────────────────────────────────────────────►

主线程   ①捞题(3道) ②建执行器 ③建信号量 ④for循环提交3个任务
                          │
                          ├── 提交任务1 ──► 虚拟线程1 启动
                          ├── 提交任务2 ──► 虚拟线程2 启动
                          └── 提交任务3 ──► 虚拟线程3 启动（但拿不到车位，等）
                                                              │
虚拟线程1     [拿车位(2→1)] [调AI.2秒...........] [写库] [还车位(1→2)] [进度=1]
虚拟线程2     [拿车位(1→0)] [调AI.3秒.................] [写库] [还车位] [进度=2]
虚拟线程3                    (等着...)                      [拿到车位] [调AI.1.5秒] [写库] [还车位] [进度=3]
                                                                                    │
主线程                                                            ⑤ try 结束，close() 等全部完成
                                                                  ⑥ 打印"成功3题 失败0题"
```

**几个关键点**：

| 观察 | 说明 |
|---|---|
| 任务 3 一开始**拿不到车位** | 因为前两个占满了（并发度=2），它必须等 |
| 谁先完成**不确定** | 任务 2 调 AI 用了 3 秒，任务 1 只用了 2 秒 → 任务 1 先完成。**每次跑顺序都可能不同** |
| 主线程卡在 `}` 那一行 | 等所有虚拟线程结束才往下走 |
| `done` 从 1 数到 3 | 靠 `AtomicInteger` 保证不数错 |

# 第 4 章：初学者最容易犯的 6 个错

### ❌ 1. 忘了 try-with-resources，方法提前返回

```java
// 错误
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
for (...) executor.submit(...);
log.info("结束");     // ← 任务还在跑，这里就说结束了
```

**后果**：进度不对、状态不对，但**不报错**（最难查的那种 bug）。

### ❌ 2. `release()` 忘了放 `finally`

```java
// 错误
limiter.acquire();
干活();              // 抛异常
limiter.release();   // 永远不执行 → 名额泄漏
```

**后果**：跑几次后所有任务都在等，程序看起来"卡死"。

### ❌ 3. 用普通 `int` 做计数器

```java
// 错误
int done = 0;
executor.submit(() -> { done++; });   // ① 编译不过（不是 final）
```

就算绕过去（比如用数组），**计数也会错**，因为 `done++` 不是原子操作。

### ❌ 4. 在 lambda 里修改外部变量

```java
// 错误：编译不过
int count = 0;
executor.submit(() -> count++);       // 报错：Variable used in lambda should be final
```

**正确**：用 `AtomicInteger`。

### ❌ 5. 锁的范围太大

```java
// 错误：把调 AI 也锁起来了
synchronized (lock) {
    enrichOne(question, aiConfig);    // 3 秒
    更新进度();
}
```

**后果**：变成串行了，并发改造完全白做。

### ❌ 6. 吞掉 `InterruptedException`

```java
// 错误
try {
    limiter.acquire();
} catch (InterruptedException e) {
    // 什么都不做 ← 中断信号被吃掉了
}
```

**后果**：服务关闭时无法优雅退出。**正确做法**：

```java
} catch (InterruptedException ie) {
    Thread.currentThread().interrupt();   // ① 把中断标志还回去
    return;                                // ② 放弃当前任务
}
```

**为什么要"还回去"**：`InterruptedException` 抛出时，Java 会**清掉线程的中断标志**。
你如果不还回去，上层代码就不知道"有人要求中断"，会继续正常干活。

# 第 5 章：面试可能怎么问

### Q：这段并发代码具体怎么写的？

> 在 `BanksServiceImpl.aiEnrich()` 里。流程是：
>
> 1. 先捞出所有还没解析成功的题（`ai_status != DONE`）
> 2. 用 `Executors.newVirtualThreadPerTaskExecutor()` 建执行器，**写在 try-with-resources 里**——因为 `close()` 会等所有任务跑完，不然方法提前返回，进度就乱了
> 3. 建一个 `Semaphore(6)` 控制同时在飞的请求数
> 4. `for` 循环里对每道题 `executor.submit(() -> {...})`，每个 lambda 里：先 `acquire()` 拿名额，然后调模型，最后在 `finally` 里 `release()`
> 5. 计数器用 `AtomicInteger`，更新进度那段用 `synchronized` 包起来

### Q：为什么要把"执行器"和"信号量"分开？

> 因为这是两个独立的需求：执行器管**怎么执行**（用虚拟线程），信号量管**同时几个**（6 个）。
>
> 如果混在一起（用固定 6 个线程的池），就被绑死在"必须有 6 个工人"上了，虚拟线程的好处也没了。
> 而且 JDK 21 的 JEP 444 里明确建议：**别用线程池限制虚拟线程的并发，用信号量**。

### Q：为什么计数器要用 `AtomicInteger`？

> 因为 `count++` 在底层是"读-改-写"三步，不是原子操作。两个线程同时做会丢更新——各加一次结果只加了 1。
>
> `AtomicInteger` 底层用 CPU 的 CAS 指令，整个操作不可分割。而且它不用锁，比 `synchronized` 包住自增性能好。

### Q：`synchronized` 锁的是什么？为什么不锁调 AI 那段？

> 锁的是一个专门 `new Object()` 出来的对象。用专门的对象是因为用 `this` 或者字符串可能被别人也拿去当锁，产生意外的互相阻塞。
>
> **不锁调 AI 那段是刻意的**——调 AI 要 3 秒，锁住就变串行了，并发改造就白做了。只锁"更新进度"那几十微秒，也就是真正需要串行的部分。原则是**锁的范围越小越好**。

### Q：`try (...)` 这个写法叫什么？为什么必须用它？

> 叫 **try-with-resources**。括号里的对象如果实现了 `AutoCloseable`，Java 会在代码块结束时**自动调它的 `close()`**，不管正常结束还是抛异常。
>
> 这里必须用，是因为 `ExecutorService.close()` 的语义是"等所有已提交的任务跑完"。而 `submit()` 是**立刻返回**的——不用这个写法的话，方法会提前往下走，日志说"解析结束"但其实还有几百个任务在跑。

### Q：如果服务中途被关掉会怎样？

> 拿信号量的地方会抛 `InterruptedException`。我的处理是：**把中断标志还回去**（`Thread.currentThread().interrupt()`），然后放弃这道题。
>
> 关键是**这道题的状态仍然是 PENDING**，所以下次续跑会被重新捞到，不会丢。
>
> 如果直接吞掉这个异常（catch 里什么都不做），服务就没法优雅关闭了。

## 附：常用并发类速查

| 类 | 一句话用途 | 我们用它干嘛 |
|---|---|---|
| `ExecutorService` | 执行任务的"包工头" | 跑并发任务 |
| `Executors` | 创建执行器的工具类 | `newVirtualThreadPerTaskExecutor()` |
| `Semaphore` | 许可证计数器，限制同时进行的数量 | 限制并发为 6 |
| `AtomicInteger` | 不会数错的整数 | 计已处理/失败题数 |
| `synchronized` | 同一时间只让一个线程进代码块 | 保护进度写库 |
| `ConcurrentHashMap` | 线程安全的 Map | 存导入任务进度快照（第 83 行，早就有了） || `InterruptedException` | 线程被要求中断时抛的异常 | 服务关闭时优雅退出 |
