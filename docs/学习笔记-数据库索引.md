# 学习笔记：数据库索引优化

> 这篇讲这次数据库索引到底改了什么、为什么这么改。
> 假设你没深入调过数据库，先打比方再讲代码。

---

## 一、索引是什么

**一句话**：索引就像书前面的目录 —— 没有它，想找"张三"这个人，得一页一页翻完整本书。

```
没有索引：把整张表所有行读出来，逐行判断是不是我要的   ← 叫"全表扫描"
有索引  ：直接跳到符合条件的位置                        ← 叫"索引查找"
```

**代价**：索引**占空间**，而且**每次写入（insert/update/delete）都要顺手更新索引**。
所以**索引不是越多越好** —— 这也是这次"只加一个"的原因。

---

## 二、先说这次审计的方法：对着真实库看，不是对着 DDL 文件看

这一步很容易被跳过，但很重要：**DDL 文件（建表脚本）和真实的库可能不一致** ——
有人手工加过索引、或者线上跑的是旧版本。

所以我直接查了真实库：

```sql
SELECT TABLE_NAME, INDEX_NAME, GROUP_CONCAT(COLUMN_NAME ORDER BY SEQ_IN_INDEX)
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = 'finaltext'
GROUP BY TABLE_NAME, INDEX_NAME;
```

**结论：12 张表，只缺一个索引。** 其余该有的都有。

---

## 三、加的那个索引

```sql
ALTER TABLE practice_record ADD KEY idx_pr_session_correct (session_id, is_correct);
```

### 为什么需要它

答题时有**两处查询**按 `(session_id, is_correct)` 过滤，而且**每提交一题就跑一遍**：

| 代码位置 | 干什么 |
|---|---|
| `PracticeSessionMapper.refreshCounts` | 重算本次会话的"已答/答对"数量（两遍 COUNT，其中一遍带 `is_correct = 1`） |
| `PracticeRecordMapper.selectWrongItems` | 查本次会话的错题明细（`is_correct = 0`） |

**原来的索引为什么不够**：

```
原有：uk_pr_session_question (session_id, question_id)
                                      ↑
                          is_correct 不在索引里！

于是：先按 session_id 框出整个会话的记录 → 全部取回来 → 再逐行判断 is_correct
```

**算一下代价**（一个 500 题的会话）：

```
每答一题 → 扫 500 行
答完 500 题 → 累计扫 500 × 500 ÷ 2 ≈ 12.5 万行
```

加上 `(session_id, is_correct)` 之后，数据库能**直接在索引里跳到匹配的项**，
不需要逐行判断。

### 列顺序为什么是 session_id 在前

这是加索引最容易搞错的地方。规则是：

```
把【区分度高、能一次筛掉最多数据】的列放前面
```

| 列 | 作用 | 放前面还是后面 |
|---|---|---|
| `session_id` | **等值过滤**，一个会话的数据聚在一起，筛完只剩几百行 | ✅ 前面 |
| `is_correct` | 只有 0/1 两个值（区分度极低），单看它没用 | ✅ 后面 |

**反例**：如果把 `is_correct` 放前面 `(is_correct, session_id)`，
数据库会先按"答对/答错"把**全库**分成两堆，再去里面找会话 —— 慢得多。

## 四、核对之后**决定不加**的索引（这部分和"加了什么"同样重要）

| 候选 | 为什么不加 |
|---|---|
| `question.bank_id` | **看起来很像该加，其实不需要** —— 已有的两个索引 `(bank_id, chapter_id)` 和 `(bank_id, type)` 都是 **bank_id 打头**，按最左前缀就能用上。再单加一个只会多占空间、拖慢写入 |
| `import_task.status` / `created_at` | 任务永远按主键 `task_id` 查（进度轮询），从不按状态扫表 |
| `chat_session.title` / `message_count` | 区分度极低，且没有查询按它们过滤 |
| `practice_record.is_correct` 单列 | 布尔列只有 2 个值，单独建索引没意义 |

### 什么是"最左前缀"

这是理解"为什么不用加 bank_id"的关键：

```
索引 (bank_id, chapter_id) 相当于一本按【先 bank、再 chapter】排好序的名册

查 bank_id = 1                    → 能直接跳到 bank 1 那一段     ✅ 用得上
查 bank_id = 1 AND chapter_id = 5 → 继续往后缩小范围             ✅ 用得上
查 chapter_id = 5                 → 名册是按 bank 排的，没法直接跳 ❌ 用不上
```

**所以：如果一个列已经是某个联合索引的第一列，就不用再单独给它建索引。**

### 一条容易被忽略的警告

> 加了**低区分度**的索引，**可能反而让查询变慢**。
>
> 因为优化器会"以为"用它能变快、结果选了个更差的执行计划。
> `is_correct` 单独建索引就是这种 —— 明明是 0/1，优化器还可能一本正经地去用它。

## 五、怎么验证索引真的生效了

用 `EXPLAIN`（意思是"让数据库告诉我，它打算怎么执行这条查询"）：

```sql
EXPLAIN SELECT COUNT(*) FROM practice_record WHERE session_id = 14 AND is_correct = 1;
```

实测结果：

```
key: idx_pr_session_correct     ← 用上我们新加的索引了
ref: const,const                ← 两个条件都是等值匹配
Extra: Using index              ← ★ 最重要：只用索引就够了，连数据行都不用读
```

**`Using index` 是什么意思**：这条查询要的答案（数量）**完全能从索引里算出来**，
不需要回到表里取数据行。这叫**覆盖索引**，是最理想的情况。

### 诚实说明：这次没法实测出"变快了"

本地库 `practice_record` **只有 7 行数据**，数据量太小，所以：

- `refreshCounts` 那条 COUNT：**已经用上新索引**（`Using index`）✅
- `selectWrongItem` 那条：优化器**还是选了旧索引**

第二条不是索引没用，而是**数据量小时索引基数太低、优化器判断不准**，
这是正常行为。数据量上去之后它会自己改选。

**所以我不能说"查询变快了多少倍"** —— 那是编的。
能说的是：**按查询模式推算，收益在 500 题以上的会话里才体现得出来。**

> 💡 **这条经验也值得记**：优化数据库时，"能用 EXPLAIN 证明它被用上了"是硬证据；
> "变快了多少"在小数据量下**往往没法证明**，这时候就别硬编数字。

## 六、索引设计的三条原则（这次都用到了）

| # | 原则 | 这次的体现 |
|---|---|---|
| 1 | **看查询，不看表** | 是 `refreshCounts` / `selectWrongItems` 的 WHERE 决定了要建 `(session_id, is_correct)`，不是"practice_record 表该有索引" |
| 2 | **联合索引的顺序 = 区分度高的在前** | `session_id`（等值、聚数据）放前，`is_correct`（只有 0/1）放后 |
| 3 | **能不建就不建** | 12 张表只加 1 个索引；`question.bank_id` 看着该加，实际被最左前缀覆盖了 |

## 七、面试可能怎么问

### Q1：你做了什么数据库优化？

> 先把 12 张表的索引对着**真实库**核了一遍（不只是看建表脚本），发现只缺一个：
> `practice_record` 少了 `(session_id, is_correct)`。
>
> 因为答题时有两条查询按这个组合过滤，而且**每提交一题就跑一遍**；
> 原有索引是 `(session_id, question_id)`，`is_correct` 不在里面，
> 所以要把整个会话的记录取回来再逐行过滤。500 题的会话累计约 12.5 万行。
>
> 加完之后 `EXPLAIN` 显示 `Using index`（覆盖索引），连回表都省了。

### Q2：为什么只加一个？

> 因为**索引不是越多越好** —— 每个索引都占空间、还会拖慢写入。
> 我核对了几个"看起来该加"的：
>
> - `question.bank_id`：已有的 `(bank_id, chapter_id)` 是 bank_id 打头，**最左前缀就能用上**，不用重复建
> - `import_task.status`：任务永远按主键查，不按状态扫表
> - `is_correct` 单列：布尔列区分度只有 2，**加了反而可能误导优化器选错计划**

### Q3：联合索引的列顺序怎么定？

> **区分度高、能一次筛掉最多数据的放前面。** `session_id` 是等值过滤、一个会话的数据聚在一起，
> 筛完只剩几百行；`is_correct` 只有 0/1，单看它没用，所以放后面。
>
> 反过来 `(is_correct, session_id)` 会先把全库按答对/答错分成两堆再找会话，慢得多。

### Q4：怎么确认索引真的生效？

> 用 `EXPLAIN`。关键看三列：
> - `key`：实际用了哪个索引
> - `ref`：是不是等值匹配
> - `Extra`：出现 **`Using index`** 说明是**覆盖索引**（只用索引就够，不回表），最好
>
> 这次实测 `refreshCounts` 那条已经是 `Using index`。

### Q5：变快了多少？

> **这个我没法给数字。** 本地库 `practice_record` 只有 7 行，数据量太小，
> 索引基数低、优化器甚至还会选旧索引 —— 这是正常的。
>
> 我能给的是**硬证据**（EXPLAIN 证明它被用上了）和**推算的收益**
> （500 题会话从扫 12.5 万行变成直接跳索引）。
> 硬编一个"快了 20 倍"是骗人的。

## 附：这次涉及的知识点

| 知识点 | 说明 |
|---|---|
| 全表扫描 vs 索引查找 | 索引就是书的目录 |
| 联合索引的最左前缀 | `(a, b)` 能用 `a`、能用 `a+b`，不能单独用 `b` |
| 覆盖索引（`Using index`） | 查询要的数据全在索引里，不用回表 —— 最理想 |
| 索引的选择性/区分度 | 0/1 这种列区分度低，单独建索引意义不大甚至有害 |
| 索引的代价 | 占空间 + 拖慢写入 → 能不建就不建 |
| `EXPLAIN` | 让数据库说出它的执行计划 |
| `information_schema.STATISTICS` | 查真实库的索引（比看 DDL 文件可靠） |
| 可重复执行的迁移脚本 | 先查 `information_schema` 判断索引/列是否存在，再决定要不要建 |
