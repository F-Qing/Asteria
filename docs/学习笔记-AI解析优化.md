# 第一部分：先搞懂问题

## 1. AI 解析在干什么

你导入一份题库，程序会做两件事：

```
第 1 步：把文档切成一道道题（纯规则，不用 AI）
第 2 步：给每道题"补解析" ← 这一步要调 AI
```

**"补解析"是什么意思**：一道题长这样——

```
题干：HTML 语言是？
A. 大型数据库   B. 网络通信协议   C. 超文本标记语言   D. 网页源文件
答案：C
```

但它**没有"解析"**——就是没有"为什么选 C"的讲解。用户刷题时看到解析才有学习效果。

所以程序要做的是：**把题目发给 AI，让 AI 写一段讲解，再存回来。**

这个动作，**一道题要发一次网络请求**。

> 💡 关键词：**一次请求 = 一次网络往返**。你发出去，等 AI 服务器算完（通常 2~5 秒），再把结果收回来。

---

## 2. 什么是"串行"，为什么它慢

**改造前**的代码是这样的（简化版）：

```java
for (Question question : questions) {     // 500 道题，循环 500 次
    result = aiEnricher.enrich(question);  // ← 每次都停在这里等 3 秒
    saveToDatabase(result);
}
```

这种"一件事做完再做下一件"的方式叫**串行**（serial）。

**打个比方：去奶茶店买 10 杯奶茶**

```
串行 = 你点 1 杯 → 等做好 → 拿走 → 再点第 2 杯 → 等做好 → 拿走 → ...
       每杯 3 分钟，10 杯 = 30 分钟
       而你其实只是在"等"，什么也没干
```

**算一下时间**：

| 题库规模 | 每道题耗时 | 总耗时 |
|---|---|---|
| 50 题 | 3 秒 | **2.5 分钟** |
| 500 题 | 3 秒 | **25 分钟** |

**问题出在哪**：程序 99% 的时间在"等网络回包"，CPU 完全是闲着的。这就像你站在奶茶店门口干等——**你完全可以同时点 10 杯，让店里一起做。**

---

## 3. 什么是"并发"，为什么它能变快

**并发**（concurrency）= 让多个任务"同时进行"，而不是一个做完再做一个。

```
并发 = 你一次性点 10 杯，然后一起等
       店里同时做，10 杯可能 4 分钟就全好了
```

**改造后**：500 道题的请求同时发出去（分批），谁先回来就先存谁的。

| 方式 | 50 题 | 500 题 |
|---|---|---|
| 串行（改造前） | 2.5 分钟 | 25 分钟 |
| 并发（改造后） | 约 27 秒 | 约 4.5 分钟 |

> ⚠️ **注意**：并发不是"把 500 个请求一次全发出去"。那样会把对方服务器打挂，你也会被限流。
> 所以真实实现要**限制同时在飞的数量**，这就是第 5 节要讲的**信号量**。

# 第二部分：三个核心概念

## 4. 虚拟线程：Java 21 的新玩具

### 先说传统线程的问题

Java 里"跑一个任务的工人"叫**线程**（Thread）。

**传统线程很贵**：每个线程要占大约 **1MB 内存**，还要操作系统分配资源。

```
你要并发 500 个请求 → 需要 500 个线程 → 500MB 内存
→ 内存扛不住，所以传统做法只能用"线程池"，最多开几十个线程
```

**线程池**的思路是："工人只有 20 个，谁空谁上"。这能解决问题，但**有个浪费**：

```
工人（线程）接到任务 → 发请求 → 然后就"干等"网络回包（3 秒）
                                   ↑
                        这 3 秒里，这个工人被占着，但什么也没干
```

### 虚拟线程怎么解决的

**Java 21 引入了虚拟线程**（Virtual Thread，代号 Loom）。

> **打个比方**：
> - **传统线程** = 正式员工，一人一个工位，坐在那儿不能动
> - **虚拟线程** = 临时工，不占工位。等他去"跑腿取外卖"（等网络）的时候，
>   工位可以立刻让给别人用

**关键点**：虚拟线程在**等待网络**的时候，会自动"让出"底层的操作系统线程。所以：

```
1000 个虚拟线程 ≈ 只占用很少的操作系统线程
→ 开几百个虚拟线程几乎不花钱
```

**代码长什么样**：

```java
// 传统写法：固定 20 个工人的线程池
ExecutorService pool = Executors.newFixedThreadPool(20);

// 虚拟线程写法：每来一个任务就新开一个虚拟线程
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
```

> ⚠️ 这几行在项目里的**具体位置**、以及完整可运行的上下文（`try (...)`、`submit`、lambda、信号量怎么配合），
> 见 [学习笔记-并发代码精讲.md](学习笔记-并发代码精讲.md) 第 0~2 章 —— 那里把每一行都拆开讲了。

⚠️ **一个重要细节**：`try (...)` 这种写法叫 **try-with-resources**。
`executor.close()` 会自动等**所有任务跑完**才返回。

```java
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Question q : questions) {
        executor.submit(() -> 处理这道题(q));
    }
}   // ← 到这里会等所有题处理完
// 这一行之后，所有题都处理完了
```

**必须这样写**，否则方法提前返回，题还在后台处理，进度就不对了。

## 5. 信号量：并发不是越多越好

### 为什么不能无限并发

想象两个问题：

**问题 1：对方服务器会不高兴**
你一次发 500 个请求，AI 服务商会认为你在攻击它，直接**限流**（返回 429 错误，意思是"你慢点"）。

**问题 2：你自己的数据库会堵住**
每道题处理完都要**写回数据库**。写数据库要用**连接**，而连接是从**连接池**里借的。

> **连接池是什么**：建立数据库连接很慢，所以程序启动时先建好一批（比如 10 条），
> 用的时候借一条、用完还回去。就像共享充电宝，不是每人买一个。

**这里有个坑**：如果你的并发度是 50，但同时只有 10 条数据库连接：

```
50 个虚拟线程同时想写数据库
   ↓
只有 10 条连接可用 → 40 个线程排队等
   ↓
并发度 50 实际上变成了 10，多出来的 40 个纯属白开
```

### 信号量怎么解决

**信号量**（Semaphore）就是一个**计数器 + 排队机制**。

> **打个比方**：停车场门口有个牌子写着"剩余车位 6"。
> - 车来了，保安看牌子：还有空位 → 放行，牌子减 1
> - 牌子显示 0 → 车在门口**排队等**，不进场
> - 有车开走 → 牌子加 1，排队的第一辆进场

**代码长什么样**：

```java
Semaphore limiter = new Semaphore(6);   // 最多 6 个同时进行

executor.submit(() -> {
    limiter.acquire();        // 拿车位：没有就等着
    try {
        调AI并写库();          // 真正干活
    } finally {
        limiter.release();    // 还车位：一定要还！
    }
});
```

⚠️ **`release()` 必须放在 `finally` 里**：不管干活成功还是失败，车位都要还。
如果忘了还，跑几次之后车位就永久少了（这叫**信号量泄漏**），最后所有任务都在门口干等。

### 为什么是 6 这个数字

```java
private static final int AI_CONCURRENCY = 6;
```

**算出来的**：
- HikariCP（默认的数据库连接池）默认给 **10 条连接**
- 但不止题目要写库，**进度、任务状态**也要写
- 所以留出余量，取 **6**

> 面试可能问："为什么是 6 不是 20？"
> 答：**因为并发度超过数据库连接数，多出来的线程只是在排队等连接，纯浪费**。
> 调大之前得先把连接池调大，并确认服务商的并发额度。

### 顺带说一个官方建议

Java 官方文档（JEP 444）里明确写了一句：

> **"不要试图用线程池来限制虚拟线程的并发，而是用信号量。"**

**为什么**：线程池是给传统线程设计的（因为线程贵，所以要复用）。
虚拟线程本来就不贵，用池反而把它的优势抹掉了。**限制并发**和**使用虚拟线程**是两件独立的事，要分开做。

## 6. "幂等"和"断点续跑"

### 什么是幂等

**幂等**（idempotent）= **同一个操作做一次和做多次，结果一样**。

| 操作 | 幂等吗 | 为什么 |
|---|---|---|
| "把名字改成张三" | ✅ 幂等 | 做 10 次结果还是张三 |
| "余额加 100" | ❌ 不幂等 | 做 10 次就加了 1000 |
| **"调 AI 生成解析"** | ❌ **不幂等** | 做 10 次 = **花 10 次钱** |

> 💡 **这是理解整个改造的关键**：
> 调 AI **不是**"再试一次也没关系"的操作，**它是真的会再扣一次钱的**。

### 所以问题在哪

改造前的代码有个隐患：

```java
for (Question question : questions) {
    result = aiEnricher.enrich(question);   // 花钱
    saveToDatabase(result);
}
```

**如果跑到第 400 题时程序崩了**（网络断了、服务重启了、你手滑关掉了）：

- 前 399 题的**钱已经花了**，解析也存进数据库了
- 但**第 400~500 题还没做**
- 你想继续 → 但是**没法知道"哪些做过了"**
- 只能**从头再跑一遍** → 前 399 题的钱**白花第二次**

### 怎么解决：给每道题记状态

**做法**：在数据库的题目表上加一列 `ai_status`，记录每道题的解析状态：

```
PENDING  还没解析过
DONE     解析成功
FAILED   解析失败（原因也存在数据库里）
```

然后**只捞没做完的题**：

```java
// 只看"还没成功"的题（PENDING 或 FAILED）
List<Question> questions = questionMapper.selectList(
        Wrappers.<Question>lambdaQuery()
                .eq(Question::getBankId, bankId)
                .ne(Question::getAiStatus, AiStatus.DONE.name())   // ← 关键：排除已完成的
);
```

**这样就实现了"断点续跑"**：

```
第一次跑：500 题全捞出来 → 处理到第 400 题崩了 → 400 题标 DONE，100 题还是 PENDING
第二次跑：只有 100 题被捞出来 → 只花这 100 题的钱
```

> 💡 **一句话总结**：**因为模型调用会花钱且不可重复，所以必须把"做过的"记下来。**

# 第三部分：数据治理

## 7. 数据血缘：这个答案是谁写的

### 先说个具体场景

一道题**文件里没给答案**：

```
题干：HTML 语言是？
A. 大型数据库   B. 网络通信协议   C. 超文本标记语言   D. 网页源文件
答案：            ← 空的！
```

程序会让 AI 顺便把答案解出来，存进数据库。**这时候问题来了**：

```
数据库里这一行：
题干：HTML 语言是？
答案：C            ← 这个 C 是谁写的？
```

**两种情况混在一起了**：
- 情况 A：文件里本来就写了 `答案：C`
- 情况 B：文件里没写，是 **AI 猜的 C**

**用户看到的是同一条数据，但可信度完全不同。**

### 为什么这是问题

想象三个月后你想做这些事：

| 你想做的事 | 需要什么 | 没有血缘会怎样 |
|---|---|---|
| 检查 AI 补的答案对不对 | 知道**哪些**答案是 AI 补的 | 500 道题一个个看，不知道看哪个 |
| 把 AI 改的答案全回滚 | 知道**原答案**是什么 | 原答案已经被覆盖，**找不回来了** |
| 统计"多少题靠 AI 才做出来" | 计数 | 数不出来 |

> 💡 **这个"知道数据从哪来"的概念，术语叫「数据血缘」（data lineage）。**

### 怎么做的

加一列 `answer_source`：

```
FILE   从上传文件里解析出来的（最可信）
AI     文件里没有，模型解出来的
MANUAL 人工改的（预留给以后的校对功能）
```

**代码里的关键逻辑**：

```java
if (result.answerFromAi()) {
    // 只有"原本缺答案、这次由模型补出来"才动 answer
    patch.setAnswer(result.answer());
    patch.setAnswerSource(AnswerSource.AI.name());   // ← 标记来源
}
// 原本就有答案的题，这里什么也不做 —— 文件里的答案比模型的可信
```

⚠️ **注意一个细节**：`answerFromAi()` 这个标记是从哪来的？

我改 `QuestionAiEnricher` 的返回值时，把"答案是不是 AI 给的"单独标了出来：

```java
public record EnrichResult(String analysis, String answer, boolean answerFromAi) {
    static EnrichResult analysisOnly(String analysis)              // 只补了解析
    static EnrichResult withAnswer(String analysis, String answer)  // 连答案一起补了
}
```

**为什么不直接判断 `answer != null`**：因为那样**语义不清晰** —— 看代码的人不知道 `null` 是"没答案"还是"不要改"。
单独一个 `answerFromAi` 字段，把"这个答案是模型写的"这一件事**显式表达出来**了。

## 8. 解析失败了怎么办：区分"一道题的错"和"账号的错"

这一节讲的是后来的一个改进。**它解决的是一个很实际的问题**：

> 用户上传题库、勾了 AI 解析，跑完之后**有几道题没有解析**。
> 界面只说"导入完成"，用户看到有些题是空的，**不知道是系统坏了还是自己有问题**。

### 8.1 先想清楚：失败分两种，处理方式完全相反

这是整节的核心。**很多人会一视同仁地处理，那是错的。**

| | **单题失败** | **账号级失败** |
|---|---|---|
| 例子 | 这道题模型答得不好、超时了、返回格式不对 | **余额不足**、**被限流（429）**、**API Key 失效** |
| 影响范围 | **就这一道题** | **接下来每一道题都会失败** |
| 该怎么办 | **跳过它，继续跑完剩下的** | **立刻停手**，别再白跑了 |
| 用户的感受 | 一道题没解析，无所谓 | "我的钱/Key 有问题" |

**为什么账号级失败必须"立刻停手"**：

```
余额不足的情况下，继续跑 500 道题会发生什么？
→ 500 次请求，500 次都失败
→ 用户白等好几分钟
→ 最后看到"全部失败"，还是不知道是余额的问题（除非提示写清楚了）
```

**打个比方**：
- 单题失败 = 一道菜做糊了 → 继续做别的菜
- 账号级失败 = **煤气停了** → 锅里所有菜都做不了，应该马上关火告诉用户，而不是把剩下的菜谱全试一遍

### 8.2 关键设计：三道防线

#### 防线一：单题失败就跳过，不影响整批

改之前的想法是"一道题失败就让整批失败"。**这是不对的** —— 用户要的是"能用"，不是"完美"。

```java
try {
    enrichOne(question, aiConfig);      // 调模型 + 写回解析
} catch (Exception e) {
    failed.incrementAndGet();           // 记一笔
    markEnrichFailed(question, aiConfig, e);   // 标 FAILED + 存失败原因
    // ★ 注意：这里不往外抛异常。这一道题失败，其他题照跑
}
```

**结果**：50 道题里失败 3 道 → 题库照常建成，47 道有解析，**3 道只是没有解析** → 用户能正常刷题。

> 💡 **这个判断很重要**：一道题失败**不该毁掉整批**。用户损失 3 道题的解析，总好过损失全部 50 道。

#### 防线二：识别"账号级失败"，立刻标记

怎么知道这次失败是"一道题的错"还是"账号的错"？

**看错误信息里的关键词**。下面是真实会出现的报文：

| 服务商的回话 | 说明什么 |
|---|---|
| `Insufficient Balance` / `insufficient_quota` | 余额不足 |
| `Rate limit reached` / `Too many requests` | 被限流 |
| `Error code: 402` / `429` / `401` | 余额不足 / 限流 / Key 失效 |
| 中文的「余额」「欠费」「限流」「频率」 | 同上，国内服务商常回中文 |

```java
private boolean isSystemicAiFailure(Throwable e) {
    // 沿异常链一层层找 —— 错误码往往包在底层异常里，不在最外层
    for (int depth = 0; t != null && depth < MAX_CAUSE_DEPTH; depth++) {
        String msg = t.getMessage();
        // 命中任一关键词 → 这是账号级问题
    }
}
```

**两个容易忽略的坑**（我实际踩到了）：

**坑 1：错误信息可能在"异常链"的深处**

Java 的异常可以套娃：

```
BusinessException("调用失败")
   └─ cause: HttpClientException
        └─ cause: ApiException("Insufficient Balance")   ← 真正的原因在这里
```

所以**不能只看最外层异常的 message**，要沿着 `getCause()` 一层层往下找。

**坑 2：异常链可能有环，会死循环**

正常是 `A → B → C` 到尽头（cause 为 null）。但如果有 bug 造成 `A → B → A` 这样的环：

```java
for (Throwable t = e; t != null; t = t.getCause()) {   // ← 永远出不来！
```

**怎么防**：加一个深度上限。

```java
private static final int MAX_CAUSE_DEPTH = 10;   // 正常异常链只有 2~3 层，10 层足够且不会误伤
```

> 💡 为什么不用 `t == t.getCause()` 判断自引用就够了？
> **因为那只防得住"A 的 cause 是自己"**，防不住 `A → B → A` 这种**环**。
> 这是我给这段代码专门写了个测试用例才发现的。

#### 防线三：把"标错的失败"改回来

这个很微妙，但**对用户体验影响很大**。

**问题**：账号级失败时，前面那些题已经被标成了 `FAILED`。但**它们失败的原因在账号，不在题目本身**。

```
标 FAILED  →  界面上这些题看起来像"解析失败了"（用户以为题目有问题）
标 PENDING →  界面上这些题是"还没解析"（实话）
```

**所以账号级失败时，要把刚才那些 FAILED 改回 PENDING**：

```java
private void unmarkRetryableFailures(List<Question> questions) {
    // 只改本次处理过、且当前状态还是 FAILED 的题
    questionMapper.update(patch, Wrappers.<Question>lambdaQuery()
            .in(Question::getId, ids)
            .eq(Question::getAiStatus, AiStatus.FAILED.name()));   // ← 条件很重要
}
```

`ai_status = 'FAILED'` 这个条件**不能省**：它保证只改"这次刚失败的"，**不会误伤之前就成功（DONE）的题**。

### 8.3 怎么让用户知道"有多少题没解析"

**后端**：在任务状态里带上三个数字。

```java
private Integer aiDoneCount;      // 已解析完的
private Integer aiPendingCount;   // 还没解析的
private Integer aiFailedCount;    // 解析失败的
```

⚠️ **这三个数不存数据库，而是每次现算**：

```java
long done   = selectCount(... ai_status = 'DONE' ...);
long failed = selectCount(... ai_status = 'FAILED' ...);
long all    = selectCount(... bank_id = ? ...);
pending = all - done - failed;
```

**为什么不存**：`question.ai_status` **已经是唯一真相源**。再存一份就有两个真相源，写的时机稍微对不上（比如失败后重试成功），界面就会说错话，而且**没法自查**。

> 💡 这是一个通用的设计原则：**能算出来的就别存**。存储是最容易不一致的东西。

**前端**：三行代码。

```vue
<!-- 成功卡片：只有真失败才多显示这一行，没失败时纯属噪音 -->
<p class="text-muted">共识别 {{ task.totalCount }} 道题目，已整理入库</p>
<p v-if="task.aiFailedCount" class="ai-warn">
  其中 {{ task.aiFailedCount }} 道题未生成解析，不影响做题
</p>
```

**效果**：

```
✅ 导入完成
   共识别 50 道题目，已整理入库
   其中 3 道题未生成解析，不影响做题     ← 用户心里有数了
   [继续导入]  [查看题库]
```

### 8.4 一个连带发现的坑：界面在撒谎

改了失败处理之后，我通过智能体的提问发现前端失败卡片上有句话**变成假的了**：

```vue
<p class="text-muted">数据已回滚，不会产生脏数据</p>
```

**为什么原来是真话**：以前"导入失败"就意味着事务回滚，题库没建成 —— 说"数据已回滚"完全正确。

**为什么现在是假话**：加了"账号级失败"这条路之后，有**两种** `FAILED`：

| 失败类型 | 数据命运 | "数据已回滚"对吗 |
|---|---|---|
| 真失败（切不出题/入库失败） | 事务回滚，题库没建成 | ✅ 对 |
| **账号级中断（40021）** | **题库和题目已经提交了** | ❌ **错！会让人以为题库没了** |

**修法**：按错误信息的开头区分两种情况。

```ts
/** 40021 走的是「题库已入库、只是解析没做完」这条路径，和真回滚不是一回事 */
const isAiInterrupted = computed(() =>
  task.value?.errorMessage?.startsWith('AI 解析中断：') ?? false)
```

```vue
<p v-if="isAiInterrupted" class="text-muted">题目已入库，可正常使用</p>
<p v-else class="text-muted">数据已回滚，不会产生脏数据</p>
```

> 💡 **这个 bug 的性质值得记住**：
> 它**不是代码写错了，而是"前提变了"** —— 同一句话在旧逻辑下是对的，加了新分支之后就变成误导。
> 这类问题**编译器不会报错、测试也不一定覆盖**，只能靠"改了行为之后回头检查所有相关的文案和注释"。

### 8.5 又一个坑：长文本把重要信息挤掉了

还是智能体发现、我来确认的。看这条错误信息的拼装：

```java
"AI 解析中断：" + aiOutcome.systemicReason()
        + "。已完成 " + completed + " 道题的解析..."
```

**问题**：这条消息最终会被 `briefReason()` **截断到 200 字**：

```java
return firstLine.length() > MAX_REASON_LENGTH
        ? firstLine.substring(0, MAX_REASON_LENGTH)   // 200 字
        : firstLine;
```

而 `systemicReason` 是**服务商原样回显的报文**，可能上百字。算一下：

```
固定部分（"AI 解析中断：" + "。已完成 … 道题的解析…"）  ≈ 49 字
留给原因的空间  200 - 49 = 151 字
真实的 402 报文  约 130~140 字   ← 卡在边界上！
```

**结果**：报文短的时候能显示"已完成 N 道"，**报文一长就被截掉** —— 而"已完成 N 道 / 还差 M 道"恰恰是用户最需要知道的信息。

**修法：把长文本挪到最后。**

```java
// ✅ 关键信息在前，长报文在后
"AI 解析中断：已完成 " + completed + " 道，还有 " + failed + " 道未解析"
        + "（已完成的题目可以正常使用）。请检查 AI 账号后重新上传以补齐。原因："
        + aiOutcome.systemicReason()
```

**这样即使被截断，用户仍然能看到**：
- ✅ 已完成多少、还差多少
- ✅ 这些题能用
- ✅ 下一步该干什么
- ⚠️ 只有"具体原因"可能被截短（但至少看到开头）

> 💡 **通用原则**：**要截断的文本，把不重要的放后面。**
> 写日志、写错误消息时，"谁在乎的顺序" = "该放前面的顺序"。

### 8.6 一句话总结这一节

> **一道题失败 ≠ 整批失败。**
> 单题失败就跳过（用户能用剩下的），账号级失败就立刻停手并说清原因（别白跑、别让用户猜）。
>
> 三个具体动作：**跳过单题失败** + **识别账号级失败** + **把标错的失败改回未解析**。
> 再配上一句给用户看的数字：「其中 N 道题未生成解析，不影响做题」。

# 第四部分：面试怎么答

## 9. 面试问答

### Q1：你做了什么优化？

> AI 补解析原来是一道题一次模型调用、**完全串行**的。500 道题要等 500 次网络往返，大概 25 分钟。
>
> 我改成了**虚拟线程并发**，用信号量把同时在飞的请求控制在 6 个以内，500 题大概 4~5 分钟。
>
> 同时做了另外两件更要紧的事：**断点续跑**和**数据血缘**。

### Q2：为什么用虚拟线程，不用普通线程池？

> 这个任务是典型的 **I/O 密集**——时间几乎全花在等模型回包上，CPU 基本闲着。
>
> 普通线程一个约 1MB 栈内存，开几百个不划算，所以传统做法只能用几十个的线程池。但线程池里的线程在"等网络"时是被占住的，白白浪费。
>
> 虚拟线程在等 I/O 时会自动让出底层操作系统线程，所以开几百个也很便宜。Java 21 原生支持。

### Q3：那为什么还要信号量？不是虚拟线程很便宜吗？

> 两个原因：
>
> 一是**对方服务器**。一次发几百个请求会被服务商限流（429）。
>
> 二是**我自己的数据库**。每道题处理完要写回结果，而写库要从连接池借连接。连接池默认 10 条，我并发开 6 是留了余量。**如果并发度超过连接数，多出来的线程只是在排队等连接，并发就白开了。**
>
> 顺带一提，Java 官方文档（JEP 444）也明确建议：**别用线程池去限制虚拟线程的并发，用信号量**。这两件事应该解耦。

### Q4：为什么并发度是 6？

> 按数据库连接池反推的。HikariCP 默认 10 条连接，但除了写题目，进度和任务状态也要写库，所以留余量取 6。
>
> 调大之前得同时确认两件事：服务商的并发额度，以及连接池有没有跟着调大。

### Q5：什么是"断点续跑"，为什么需要它？

> 模型调用**不是幂等的**——重试一次就真的再付一次钱。
>
> 原来的代码没有记录"哪些题处理过了"。如果跑到第 400 题崩了，想继续就只能从头再跑，前 399 题的钱白花第二次。
>
> 我在题目表加了 `ai_status`（PENDING/DONE/FAILED），每次只捞没到 DONE 的题。这样重跑只处理没做完的，不重复付费。
>
> 失败的题会标成 FAILED 并把原因存下来，下次续跑时自然会被重新捞出来重试。

### Q6：什么是数据血缘，你为什么做这个？

> 有些题文件里没给答案，程序会让 AI 顺便解出来。**这时候数据库里就分不清"这个答案是文件里写的，还是 AI 猜的"了。**
>
> 两者可信度差很多。如果不记录来源，将来想做"人工复核 AI 补的答案"或者"回滚 AI 的改动"，会发现**原始数据已经被覆盖，什么都做不了**。
>
> 我加了 `answer_source` 列（FILE/AI/MANUAL），并且在写回逻辑里保证：**题目原本有答案时，绝不用 AI 的结果覆盖**——文件里的答案比模型的可信。

### Q7：怎么保证并发下的正确性？

> 三个点：
>
> **进度计数用 `AtomicInteger`**，因为多个线程会同时 +1。
>
> **写进度要加锁**，因为多个线程同时更新同一行任务记录会互相覆盖。
>
> **信号量的 `release()` 放在 `finally`**——不管成功失败都要还名额，否则跑几次名额就漏光了，最后所有任务都在等待。

### Q8：中途被中断（比如服务关闭）会怎样？

> 我在拿信号量的地方处理了 `InterruptedException`：把中断标志还回去（`Thread.currentThread().interrupt()`）然后放弃这道题。
>
> 关键是**这道题仍然是 PENDING 状态**，所以下次续跑会被重新捞到，**不会丢**。

### Q9：这个改造有什么已知的不足？

> 说三个真实的：
>
> **一、还没做批量调用**。现在仍然是"一题一次请求"，只是并发起来了。把多道题打包成一次请求（比如一次 10 题）还能进一步减少请求数。**但这里有个权衡**：模型服务商是按"前缀缓存"计费的，请求前缀完全一致才能命中缓存；批量会改变请求结构，得实测才能确定是否更划算。
>
> **二、"续跑"没有界面入口**。后端确实做到了"已解析的题不重复花钱"（见 [第 6 节](#6-幂等和断点续跑)），但用户**没有按钮**去触发它 —— 现在只有"重新上传"（会建新题库、全部重新解析）。这是刻意的取舍：加续跑入口要引入新接口 + 前端按钮 + 任务状态机，**为省几道题的 token 不值得**。失败的题不多时，用户直接用没解析的部分照样能刷题。

### Q10：一道题解析失败，会不会毁掉整批？

> **不会，这是刻意设计的。** 单题失败在 `catch` 里只做两件事：计数 + 把那道题标成 FAILED，**不往外抛异常**。所以其他题照常跑完，题库正常建成。
>
> 判断依据是：用户要的是"能用"，不是"完美"。50 道题里失败 3 道，用户损失 3 道题的解析，总好过损失全部。

### Q11：那如果失败原因是"余额不足"呢？也跳过？

> **不一样，这种要立刻停手。** 我把失败分成两类：
>
> - **单题失败**（模型抽风、超时）→ 跳过，继续跑
> - **账号级失败**（余额不足、限流 429、Key 失效）→ 停手 + 明确告诉用户
>
> 区别在于**影响范围**：余额不足的情况下，**接下来每一道题都会失败**。继续跑 500 道就是白等好几分钟、白跑 500 次请求，最后用户还是不知道是余额的问题。
>
> 就像一道菜做糊了可以继续做别的，但**煤气停了就该关火**，不该把菜谱全试一遍。

### Q12：怎么判断一个错误是"账号级"的？

> 沿着**异常链**找关键词。链是关键 —— 错误码往往包在底层异常里，最外层只写着"调用失败"：
>
> ```
> BusinessException("调用失败")
>    └─ cause: HttpClientException
>         └─ cause: ApiException("Insufficient Balance")   ← 真正原因在这
> ```
>
> 关键词覆盖中英文：`insufficient` / `quota` / `rate limit` / `too many requests` / `balance`，以及「余额」「欠费」「限流」「频率」，还有状态码 `401` / `402` / `429`。
>
> **两个坑我都踩了**：
> 1. **只看最外层异常会漏判** —— 必须沿 `getCause()` 往下找
> 2. **异常链可能有环，会死循环** —— 所以我加了深度上限 `MAX_CAUSE_DEPTH = 10`。光判断"cause 是不是自己"不够，因为 `A → B → A` 这种环它发现不了

### Q13：账号级失败时，那些已经标失败的题怎么办？

> **改回"未解析"状态。** 因为**它们失败的原因在账号，不在题目本身** —— 标成 FAILED 会让界面显示"这些题解析失败了"，误导用户以为题目有问题；标成 PENDING 表达的才是实话："只是还没解析"。
>
> 改的时候有个关键条件：`WHERE id IN (...) AND ai_status = 'FAILED'`。这个 `ai_status = 'FAILED'` **不能省** —— 它保证只改这次刚失败的题，**不会误伤之前就已经解析成功（DONE）的题**。

### Q14：用户怎么知道有多少题没解析？

> 后端在任务状态里带三个数（已完成 / 待解析 / 失败），前端在成功卡片上显示一行：
> 「其中 3 道题未生成解析，不影响做题」。
>
> **这三个数是每次现算的，不存数据库**。因为 `question.ai_status` 已经是唯一真相源，再存一份就有两个真相源，写的时机稍微对不上界面就说错话。**能算出来的就别存**。

### Q15：这批改动里你踩过什么"非技术"的坑？

> 有一个很典型：**改了行为之后，界面文案变成了假话。**
>
> 失败卡片上原来写着「数据已回滚，不会产生脏数据」—— 在旧逻辑下这是**真话**，因为导入失败就意味着事务回滚、题库没建成。
>
> 但加了"账号级失败"这条路之后，有**两种** FAILED：真失败确实回滚了，而账号级中断（40021）时**题库和题目已经提交了**。同一句话从真话变成了误导 —— 用户会以为题库没了。
>
> 修法是按错误信息前缀区分，两种情况显示不同文案。
>
> **这类 bug 编译器不报错、测试也不一定覆盖**，只能靠"改了行为之后回头检查所有相关的文案和注释"。这也提醒我：**注释和文案是代码的一部分，改逻辑时要一起改。**

### Q16：还有一个坑是什么？

> **长文本把重要信息挤掉了。**
>
> 40021 的错误信息是 `"AI 解析中断：" + 服务商的原样报文 + "。已完成 N 道…"`，而这条消息最终会被**截断到 200 字**。
>
> 算一下：固定部分约 49 字，留给报文 151 字，而真实的 402 报文约 130~140 字 —— **卡在边界上**。报文一长，"已完成 N 道 / 还差 M 道"就被截掉了，而那恰恰是用户最需要知道的。
>
> 修法很简单：**把长报文挪到最后**。这样即使被截断，用户仍能看到"已完成多少、还差多少、这些题能用、下一步干什么"，只有"具体原因"可能被截短。
>
> **通用原则：要截断的文本，把不重要的放后面。**
>
> **三、`Message()` 每次轮询多 3 次 COUNT 查询**（前端 1.5 秒调一次）。现在题库是几百题规模、`bank_id` 有索引，完全无感；但如果将来单库上万题、又有多人同时轮询，应该改成一次 `GROUP BY ai_status` 聚合查询。**这是个已知的、有明确触发条件的取舍**，不是疏漏。
