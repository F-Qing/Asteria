# 第一部分：先搞懂问题

## 1. AI 解析在干什么

你导入一份题库，程序会做两件事：

```
第 1 步：把文档切成一道道题（纯规则，不用 AI）
第 2 步：给每道题"补解析" ← 这一步要调 AI
```

**"补解析"是什么意思**：一道题长这样——

```
题干：HTML 语言是？
A. 大型数据库   B. 网络通信协议   C. 超文本标记语言   D. 网页源文件
答案：C
```

但它**没有"解析"**——就是没有"为什么选 C"的讲解。用户刷题时看到解析才有学习效果。

所以程序要做的是：**把题目发给 AI，让 AI 写一段讲解，再存回来。**

这个动作，**一道题要发一次网络请求**。

> 💡 关键词：**一次请求 = 一次网络往返**。你发出去，等 AI 服务器算完（通常 2~5 秒），再把结果收回来。

---

## 2. 什么是"串行"，为什么它慢

**改造前**的代码是这样的（简化版）：

```java
for (Question question : questions) {     // 500 道题，循环 500 次
    result = aiEnricher.enrich(question);  // ← 每次都停在这里等 3 秒
    saveToDatabase(result);
}
```

这种"一件事做完再做下一件"的方式叫**串行**（serial）。

**打个比方：去奶茶店买 10 杯奶茶**

```
串行 = 你点 1 杯 → 等做好 → 拿走 → 再点第 2 杯 → 等做好 → 拿走 → ...
       每杯 3 分钟，10 杯 = 30 分钟
       而你其实只是在"等"，什么也没干
```

**算一下时间**：

| 题库规模 | 每道题耗时 | 总耗时 |
|---|---|---|
| 50 题 | 3 秒 | **2.5 分钟** |
| 500 题 | 3 秒 | **25 分钟** |

**问题出在哪**：程序 99% 的时间在"等网络回包"，CPU 完全是闲着的。这就像你站在奶茶店门口干等——**你完全可以同时点 10 杯，让店里一起做。**

---

## 3. 什么是"并发"，为什么它能变快

**并发**（concurrency）= 让多个任务"同时进行"，而不是一个做完再做一个。

```
并发 = 你一次性点 10 杯，然后一起等
       店里同时做，10 杯可能 4 分钟就全好了
```

**改造后**：500 道题的请求同时发出去（分批），谁先回来就先存谁的。

| 方式 | 50 题 | 500 题 |
|---|---|---|
| 串行（改造前） | 2.5 分钟 | 25 分钟 |
| 并发（改造后） | 约 27 秒 | 约 4.5 分钟 |

> ⚠️ **注意**：并发不是"把 500 个请求一次全发出去"。那样会把对方服务器打挂，你也会被限流。
> 所以真实实现要**限制同时在飞的数量**，这就是第 5 节要讲的**信号量**。

# 第二部分：三个核心概念

## 4. 虚拟线程：Java 21 的新玩具

### 先说传统线程的问题

Java 里"跑一个任务的工人"叫**线程**（Thread）。

**传统线程很贵**：每个线程要占大约 **1MB 内存**，还要操作系统分配资源。

```
你要并发 500 个请求 → 需要 500 个线程 → 500MB 内存
→ 内存扛不住，所以传统做法只能用"线程池"，最多开几十个线程
```

**线程池**的思路是："工人只有 20 个，谁空谁上"。这能解决问题，但**有个浪费**：

```
工人（线程）接到任务 → 发请求 → 然后就"干等"网络回包（3 秒）
                                   ↑
                        这 3 秒里，这个工人被占着，但什么也没干
```

### 虚拟线程怎么解决的

**Java 21 引入了虚拟线程**（Virtual Thread，代号 Loom）。

> **打个比方**：
> - **传统线程** = 正式员工，一人一个工位，坐在那儿不能动
> - **虚拟线程** = 临时工，不占工位。等他去"跑腿取外卖"（等网络）的时候，
>   工位可以立刻让给别人用

**关键点**：虚拟线程在**等待网络**的时候，会自动"让出"底层的操作系统线程。所以：

```
1000 个虚拟线程 ≈ 只占用很少的操作系统线程
→ 开几百个虚拟线程几乎不花钱
```

**代码长什么样**：

```java
// 传统写法：固定 20 个工人的线程池
ExecutorService pool = Executors.newFixedThreadPool(20);

// 虚拟线程写法：每来一个任务就新开一个虚拟线程
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
```

> ⚠️ 这几行在项目里的**具体位置**、以及完整可运行的上下文（`try (...)`、`submit`、lambda、信号量怎么配合），
> 见 [学习笔记-并发代码精讲.md](学习笔记-并发代码精讲.md) 第 0~2 章 —— 那里把每一行都拆开讲了。

⚠️ **一个重要细节**：`try (...)` 这种写法叫 **try-with-resources**。
`executor.close()` 会自动等**所有任务跑完**才返回。

```java
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Question q : questions) {
        executor.submit(() -> 处理这道题(q));
    }
}   // ← 到这里会等所有题处理完
// 这一行之后，所有题都处理完了
```

**必须这样写**，否则方法提前返回，题还在后台处理，进度就不对了。

## 5. 信号量：并发不是越多越好

### 为什么不能无限并发

想象两个问题：

**问题 1：对方服务器会不高兴**
你一次发 500 个请求，AI 服务商会认为你在攻击它，直接**限流**（返回 429 错误，意思是"你慢点"）。

**问题 2：你自己的数据库会堵住**
每道题处理完都要**写回数据库**。写数据库要用**连接**，而连接是从**连接池**里借的。

> **连接池是什么**：建立数据库连接很慢，所以程序启动时先建好一批（比如 10 条），
> 用的时候借一条、用完还回去。就像共享充电宝，不是每人买一个。

**这里有个坑**：如果你的并发度是 50，但同时只有 10 条数据库连接：

```
50 个虚拟线程同时想写数据库
   ↓
只有 10 条连接可用 → 40 个线程排队等
   ↓
并发度 50 实际上变成了 10，多出来的 40 个纯属白开
```

### 信号量怎么解决

**信号量**（Semaphore）就是一个**计数器 + 排队机制**。

> **打个比方**：停车场门口有个牌子写着"剩余车位 6"。
> - 车来了，保安看牌子：还有空位 → 放行，牌子减 1
> - 牌子显示 0 → 车在门口**排队等**，不进场
> - 有车开走 → 牌子加 1，排队的第一辆进场

**代码长什么样**：

```java
Semaphore limiter = new Semaphore(6);   // 最多 6 个同时进行

executor.submit(() -> {
    limiter.acquire();        // 拿车位：没有就等着
    try {
        调AI并写库();          // 真正干活
    } finally {
        limiter.release();    // 还车位：一定要还！
    }
});
```

⚠️ **`release()` 必须放在 `finally` 里**：不管干活成功还是失败，车位都要还。
如果忘了还，跑几次之后车位就永久少了（这叫**信号量泄漏**），最后所有任务都在门口干等。

### 为什么是 6 这个数字

```java
private static final int AI_CONCURRENCY = 6;
```

**算出来的**：
- HikariCP（默认的数据库连接池）默认给 **10 条连接**
- 但不止题目要写库，**进度、任务状态**也要写
- 所以留出余量，取 **6**

> 面试可能问："为什么是 6 不是 20？"
> 答：**因为并发度超过数据库连接数，多出来的线程只是在排队等连接，纯浪费**。
> 调大之前得先把连接池调大，并确认服务商的并发额度。

### 顺带说一个官方建议

Java 官方文档（JEP 444）里明确写了一句：

> **"不要试图用线程池来限制虚拟线程的并发，而是用信号量。"**

**为什么**：线程池是给传统线程设计的（因为线程贵，所以要复用）。
虚拟线程本来就不贵，用池反而把它的优势抹掉了。**限制并发**和**使用虚拟线程**是两件独立的事，要分开做。

## 6. "幂等"和"断点续跑"

### 什么是幂等

**幂等**（idempotent）= **同一个操作做一次和做多次，结果一样**。

| 操作 | 幂等吗 | 为什么 |
|---|---|---|
| "把名字改成张三" | ✅ 幂等 | 做 10 次结果还是张三 |
| "余额加 100" | ❌ 不幂等 | 做 10 次就加了 1000 |
| **"调 AI 生成解析"** | ❌ **不幂等** | 做 10 次 = **花 10 次钱** |

> 💡 **这是理解整个改造的关键**：
> 调 AI **不是**"再试一次也没关系"的操作，**它是真的会再扣一次钱的**。

### 所以问题在哪

改造前的代码有个隐患：

```java
for (Question question : questions) {
    result = aiEnricher.enrich(question);   // 花钱
    saveToDatabase(result);
}
```

**如果跑到第 400 题时程序崩了**（网络断了、服务重启了、你手滑关掉了）：

- 前 399 题的**钱已经花了**，解析也存进数据库了
- 但**第 400~500 题还没做**
- 你想继续 → 但是**没法知道"哪些做过了"**
- 只能**从头再跑一遍** → 前 399 题的钱**白花第二次**

### 怎么解决：给每道题记状态

**做法**：在数据库的题目表上加一列 `ai_status`，记录每道题的解析状态：

```
PENDING  还没解析过
DONE     解析成功
FAILED   解析失败（原因也存在数据库里）
```

然后**只捞没做完的题**：

```java
// 只看"还没成功"的题（PENDING 或 FAILED）
List<Question> questions = questionMapper.selectList(
        Wrappers.<Question>lambdaQuery()
                .eq(Question::getBankId, bankId)
                .ne(Question::getAiStatus, AiStatus.DONE.name())   // ← 关键：排除已完成的
);
```

**这样就实现了"断点续跑"**：

```
第一次跑：500 题全捞出来 → 处理到第 400 题崩了 → 400 题标 DONE，100 题还是 PENDING
第二次跑：只有 100 题被捞出来 → 只花这 100 题的钱
```

> 💡 **一句话总结**：**因为模型调用会花钱且不可重复，所以必须把"做过的"记下来。**

# 第三部分：数据治理

## 7. 数据血缘：这个答案是谁写的

### 先说个具体场景

一道题**文件里没给答案**：

```
题干：HTML 语言是？
A. 大型数据库   B. 网络通信协议   C. 超文本标记语言   D. 网页源文件
答案：            ← 空的！
```

程序会让 AI 顺便把答案解出来，存进数据库。**这时候问题来了**：

```
数据库里这一行：
题干：HTML 语言是？
答案：C            ← 这个 C 是谁写的？
```

**两种情况混在一起了**：
- 情况 A：文件里本来就写了 `答案：C`
- 情况 B：文件里没写，是 **AI 猜的 C**

**用户看到的是同一条数据，但可信度完全不同。**

### 为什么这是问题

想象三个月后你想做这些事：

| 你想做的事 | 需要什么 | 没有血缘会怎样 |
|---|---|---|
| 检查 AI 补的答案对不对 | 知道**哪些**答案是 AI 补的 | 500 道题一个个看，不知道看哪个 |
| 把 AI 改的答案全回滚 | 知道**原答案**是什么 | 原答案已经被覆盖，**找不回来了** |
| 统计"多少题靠 AI 才做出来" | 计数 | 数不出来 |

> 💡 **这个"知道数据从哪来"的概念，术语叫「数据血缘」（data lineage）。**

### 怎么做的

加一列 `answer_source`：

```
FILE   从上传文件里解析出来的（最可信）
AI     文件里没有，模型解出来的
MANUAL 人工改的（预留给以后的校对功能）
```

**代码里的关键逻辑**：

```java
if (result.answerFromAi()) {
    // 只有"原本缺答案、这次由模型补出来"才动 answer
    patch.setAnswer(result.answer());
    patch.setAnswerSource(AnswerSource.AI.name());   // ← 标记来源
}
// 原本就有答案的题，这里什么也不做 —— 文件里的答案比模型的可信
```

⚠️ **注意一个细节**：`answerFromAi()` 这个标记是从哪来的？

我改 `QuestionAiEnricher` 的返回值时，把"答案是不是 AI 给的"单独标了出来：

```java
public record EnrichResult(String analysis, String answer, boolean answerFromAi) {
    static EnrichResult analysisOnly(String analysis)              // 只补了解析
    static EnrichResult withAnswer(String analysis, String answer)  // 连答案一起补了
}
```

**为什么不直接判断 `answer != null`**：因为那样**语义不清晰** —— 看代码的人不知道 `null` 是"没答案"还是"不要改"。
单独一个 `answerFromAi` 字段，把"这个答案是模型写的"这件事**显式表达出来**了。

# 第四部分：面试怎么答

## 8. 面试问答

### Q1：你做了什么优化？

> AI 补解析原来是一道题一次模型调用、**完全串行**的。500 道题要等 500 次网络往返，大概 25 分钟。
>
> 我改成了**虚拟线程并发**，用信号量把同时在飞的请求控制在 6 个以内，500 题大概 4~5 分钟。
>
> 同时做了另外两件更要紧的事：**断点续跑**和**数据血缘**。

### Q2：为什么用虚拟线程，不用普通线程池？

> 这个任务是典型的 **I/O 密集**——时间几乎全花在等模型回包上，CPU 基本闲着。
>
> 普通线程一个约 1MB 栈内存，开几百个不划算，所以传统做法只能用几十个的线程池。但线程池里的线程在"等网络"时是被占住的，白白浪费。
>
> 虚拟线程在等 I/O 时会自动让出底层操作系统线程，所以开几百个也很便宜。Java 21 原生支持。

### Q3：那为什么还要信号量？不是虚拟线程很便宜吗？

> 两个原因：
>
> 一是**对方服务器**。一次发几百个请求会被服务商限流（429）。
>
> 二是**我自己的数据库**。每道题处理完要写回结果，而写库要从连接池借连接。连接池默认 10 条，我并发开 6 是留了余量。**如果并发度超过连接数，多出来的线程只是在排队等连接，并发就白开了。**
>
> 顺带一提，Java 官方文档（JEP 444）也明确建议：**别用线程池去限制虚拟线程的并发，用信号量**。这两件事应该解耦。

### Q4：为什么并发度是 6？

> 按数据库连接池反推的。HikariCP 默认 10 条连接，但除了写题目，进度和任务状态也要写库，所以留余量取 6。
>
> 调大之前得同时确认两件事：服务商的并发额度，以及连接池有没有跟着调大。

### Q5：什么是"断点续跑"，为什么需要它？

> 模型调用**不是幂等的**——重试一次就真的再付一次钱。
>
> 原来的代码没有记录"哪些题处理过了"。如果跑到第 400 题崩了，想继续就只能从头再跑，前 399 题的钱白花第二次。
>
> 我在题目表加了 `ai_status`（PENDING/DONE/FAILED），每次只捞没到 DONE 的题。这样重跑只处理没做完的，不重复付费。
>
> 失败的题会标成 FAILED 并把原因存下来，下次续跑时自然会被重新捞出来重试。

### Q6：什么是数据血缘，你为什么做这个？

> 有些题文件里没给答案，程序会让 AI 顺便解出来。**这时候数据库里就分不清"这个答案是文件里写的，还是 AI 猜的"了。**
>
> 两者可信度差很多。如果不记录来源，将来想做"人工复核 AI 补的答案"或者"回滚 AI 的改动"，会发现**原始数据已经被覆盖，什么都做不了**。
>
> 我加了 `answer_source` 列（FILE/AI/MANUAL），并且在写回逻辑里保证：**题目原本有答案时，绝不用 AI 的结果覆盖**——文件里的答案比模型的可信。

### Q7：怎么保证并发下的正确性？

> 三个点：
>
> **进度计数用 `AtomicInteger`**，因为多个线程会同时 +1。
>
> **写进度要加锁**，因为多个线程同时更新同一行任务记录会互相覆盖。
>
> **信号量的 `release()` 放在 `finally`**——不管成功失败都要还名额，否则跑几次名额就漏光了，最后所有任务都在等待。

### Q8：中途被中断（比如服务关闭）会怎样？

> 我在拿信号量的地方处理了 `InterruptedException`：把中断标志还回去（`Thread.currentThread().interrupt()`）然后放弃这道题。
>
> 关键是**这道题仍然是 PENDING 状态**，所以下次续跑会被重新捞到，**不会丢**。

### Q9：这个改造有什么已知的不足？

> 有，我说三点：
>
> **一、进度落库每 5 题一次**，所以崩溃时最多丢 5 题的进度记录。不过这只影响进度显示，不影响实际数据——每道题的成功/失败是各自落的，续跑是以题目状态为准的。
>
> **二、还没做批量调用**。现在仍然是"一题一次请求"，只是并发起来了。把多道题打包成一次请求（比如一次 10 题）还能进一步减少请求数。**但这里有个权衡**：模型服务商是按"前缀缓存"计费的，请求前缀完全一致才能命中缓存；批量会改变请求结构，得实测才能确定是否更划算。
>
> **三、失败没有限制重试次数**。现在有 `ai_retry_count` 这一列在记，但还没有"失败 N 次就不再试"的逻辑。一直失败的题在每次续跑时都会被重新捞出来。这是个待办。
