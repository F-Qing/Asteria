## 一、LaTeX 反斜杠炸掉 JSON 解析

### 1.1 现象

题库里有数学/物理题，题干含 LaTeX 公式。走 AI 抽取路径时会出现两种都很糟的结果：

- **整批导入失败**，报"AI 抽取失败"
- 或者**题干悄悄变样**了，比如 `\frac{1}{2}` 变成 `rac{1}{2}`（前面的字符没了）

第二种最危险 —— 用户看不出来，数据已经脏了。

### 1.2 根因

一句话：**反斜杠在 JSON 里是转义符，在 LaTeX 里是命令前缀，两者冲突。**

模型被要求"输出 JSON"，它会忠实地把公式写进去：

```json
{"stem": "求 \frac{1}{2} + \frac{1}{3} 的值"}
```

这串文本交给 Jackson（Spring Boot 默认的 JSON 解析器）时，`\` 被当成了**转义开始符**，于是分成两类坏法：

| 反斜杠 + 字符 | JSON 规范怎么看 | 后果 |
|---|---|---|
| `\f`（\frac） | **合法**转义 → 换页符 U+000C | Jackson 不报错，解析成「换页符 + rac」→ **静默损坏** |
| `\b`（\beta） | **合法**转义 → 退格符 U+0008 | 同上 → **静默损坏** |
| `\v`（\vdots） | **合法**转义 → 垂直制表符 | 同上 |
| `\a`（\alpha） | **非法**转义 | Jackson 抛 `JsonParseException` → 整块抽取失败 → 重试仍失败 → **整批导入报错** |
| `\t`（\times） | **合法**转义 → 制表符 | 静默损坏，**且无法安全修复**（见 1.6） |

关键点：**`\f` `\b` `\v` 是"合法的坏法"** —— 程序不报错，数据却坏了。这是这个 bug 最阴的地方。

### 1.3 怎么发现的

不是猜的，是三步定位：

1. **读代码**：确认 `AiQuestionExtractor.parseQuestions()` 用 `objectMapper.readTree(json)` 解析模型输出
2. **查配置**：全项目 grep `ObjectMapper` / `JsonReadFeature` / `configure(` —— **没有任何自定义 Jackson 配置**，用的是 Spring Boot 默认实例，也就是**严格按 JSON 规范处理转义**
3. **看清洗逻辑**：`stripToJson()` 只做两件事 —— 去掉 markdown 围栏、截掉第一个 `{` 之前的内容。**完全不碰转义**

同时确认这个 bug 影响**三条路径**（不只是抽取）：

| 路径 | 位置 | 用的解析方式 |
|---|---|---|
| AI 结构化抽取 | `AiQuestionExtractor` | 直接 `objectMapper.readTree` |
| 逐题补解析 | `QuestionAiEnricher` | Spring AI 的 `BeanOutputConverter` |
| 知识点总结 / 易错点 | `AiServiceImpl` | 同上 |

`BeanOutputConverter` 我特意去反编译看了（`javap -p`）：它内部就是一个普通 `ObjectMapper`，自带的清理器只有 `MarkdownCodeBlockCleaner`（去围栏）和 `WhitespaceCleaner`（去空白），**没有反斜杠修复**。所以三条路径都得自己处理。

### 1.4 第一版解法（错的，但有价值）

**思路**：既然是"非法转义导致解析失败"，那就把**非法的**反斜杠补成合法的 —— 遇到 `\` 判断下一个字符：

- `\n \t \r \b \f \" \\ \/ \uXXXX` → 合法，原样保留
- 其余（`\frac` `\alpha`）→ 补成 `\\`

**结果**：`\alpha` 那类确实修好了（不再抛异常），但 `\frac` **照样坏**。

因为 `\f` 在 JSON 里合法，所以按"保留合法转义"的规则走，它被原样放过 → 到了 Jackson 那里还是被解析成换页符。

**这一版让我想明白了问题的本质**：

> 这不是"修复非法转义"的问题，而是 **JSON 的转义语义和 LaTeX 命令语法天然冲突** ——
> 只要算法尊重 JSON 语义，`\frac` 就一定会坏。光靠文本层修复**不可能**完全解决。

### 1.5 第二版解法（现在的实现）

在"保留合法转义"之上加一条**启发式规则**：

```java
// 反斜杠 + f/b/v + 紧跟小写字母 → 几乎不可能是真的控制字符，当 LaTeX 命令处理
if (isControlEscape(next) && isAsciiLower(text.charAt(i + 2))) {
    sb.append("\\\\").append(next);   // 补成 \\f
    i++;
    continue;
}
```

**为什么这条判据安全**：真的换页符后面不会正好跟一个小写字母。真换页符的典型场景是"第一页`<FF>`第二页"（后面是文字）或行尾。

实测效果：

| 输入 | 修复前 | 修复后 |
|---|---|---|
| `\frac{1}{2}` | `rac{1}{2}`（换页符被吞） | `\frac{1}{2}` ✅ |
| `\beta` | `eta`（退格符） | `\beta` ✅ |
| `\alpha` | **抛异常** | `\alpha` ✅ |
| 真换页符「第一页`<FF>`第二页」 | — | 原样保留 ✅ |

### 1.6 已知覆盖不到的情况（重要，别吹牛）

`\times`（变成 tab + "imes"）和 `\nabla`（变成换行 + "abla"）**修不了**，而且这是**刻意的**：

`\t` 和 `\n` 在正文里是**真会用到的**字符（制表、换行）。如果按"`\t` 后面跟字母就当 LaTeX"来修，就会把正常的"`<TAB>`imes"误改成 `\times` —— 用一个更隐蔽的错误换掉另一个错误。

**那怎么办？从源头约束 + 兜底：**

1. **改提示词**：在 `AiQuestionExtractor` 和 `QuestionAiEnricher` 的系统提示词里明确要求
   「反斜杠必须写成两个：写 `"\\frac{1}{2}"` 而不是 `"\frac{1}{2}"`」
2. **代码兜底**：能修的四类（`\f` `\b` `\v` 非法类）在 `AiJsonRepair` 里修
3. **接受残余风险**：`\times` / `\nabla` 属于已知局限，写进注释

> **面试可以主动说这个取舍** —— 能讲清"为什么这一类不修"比"我全修了"更可信。

### 1.7 一个意外的插曲

第一版代码**编译不过**，报 5 个「非法的 Unicode 转义」错误 —— 位置全在我自己写的 Javadoc 注释里。

原因：**Java 编译器在词法分析的**最早期**就会处理整个源文件的 `\uXXXX` 序列，注释也不例外**（JLS 3.3）。我为了举例写了 `\uXXXX`，编译器真去解析它，发现后面不是合法的 4 位十六进制 → 报错。

**这个知识点本身就很适合放进面试话题**：Java 里 `\u` 转义先于注释处理，所以注释里也不能随便写 `\u`。

### 1.8 改动的文件

| 文件 | 改动 |
|---|---|
| `AiJsonRepair.java` | **新增**，共享的转义修复工具（静态类，无 Spring 依赖） |
| `AiQuestionExtractor.java` | `stripToJson` 后接修复；系统提示词加第 8 条 |
| `QuestionAiEnricher.java` | 解析前修复；提示词加第 4 条 |
| `AiServiceImpl.java` | 两处 `converter.convert()` 前修复 |
| `AiJsonRepairTest.java` | **新增**，16 个用例 |
| `AiErrors.java` | 顺手修了 `config` 为 null 时的 NPE |

## 二、解析结果的自检（答案越界探针）

### 2.1 为什么加这个

切题切错了，程序是**不知道**的。一道题可以"看起来入库成功"，实际上题干被切成了两半、答案配到了别的题上。

在没有度量手段之前，你只能说"感觉识别得还行" —— 这对改进没有任何帮助。

### 2.2 六条确定性规则

`QuestionQualityCheck` 检查这些（**只打标、不改数据、不阻断导入**）：

| 检查项 | 判据 | 价值 |
|---|---|---|
| 无题干 | 题干为空 | 入库时本来就会被跳过，提前报出来 |
| 缺答案 | 没提取到答案 | 不开 AI 时无法判分 |
| 选项不足 | 判成单选/多选却少于 2 个选项 | 大概率切错 |
| **答案越界** | **答案字母不在选项字母集合里** | ⭐ **最可靠的问题信号** |
| 选项重复 | 同一题里出现两个 A | 切块错位 |
| 有可疑行 | 解析器收块时没认出来的行 | 第一次真正使用 `RawQuestion.suspicious` |

**「答案越界」为什么最有价值**：答案 D 但选项只有 A/B/C —— 这种情况几乎不可能是"题目本身如此"，**一定是切题切错了**。所以它相当于一个**免费的错误探针**：不用人工核对，跑一次导入就知道这批数据的健康度。

举个真实场景：教辅书里答案统一放在文末，切题时答案行配错了位 → 一批题全部"答案越界"。以前你要一题一题翻，现在日志直接告诉你「发现 12 处答案越界」。

### 2.3 顺带解决的一个历史遗留

`RawQuestion.suspicious` 这个字段**以前是"只写不读"的**：`QuestionParser` 往里塞了内容，但下游从来没人看。这次自检第一次真正利用它 —— 等于把一个死字段变成了可用信号。

### 2.4 一个被砍掉的功能（诚实记录）

我原本还设计了「题号跳号」检查（题号不连续 → 可能漏切了一道题），**写完才发现做不了**：

> `QuestionParser` 在切题时已经把题号从题干里剥掉了，`RawQuestion` 也没保留原始题号 —— 所以拿不到两个题号做比较。

要做得先让 `RawQuestion` 带上题号字段。我选择**砍掉而不是硬凑**（比如从行号差推断，那会产生大量误报，反而让探针失去意义）。

**这条也值得在面试里讲**：认识到"某个检查做不了"并说明原因，比硬做一个误报满满的检查更专业。

### 2.5 为什么放在导入流程里

```
文件解析 → 【自检打标】 → 入库事务 → AI 解析
              ↑
        放在入库前，这样日志里的问题能和紧接着的入库统计对上
```

### 2.6 改动文件

| 文件 | 改动 |
|---|---|
| `QuestionQualityCheck.java` | **新增**，`@Component`，`check(List<RawQuestion>) → Report` |
| `BanksServiceImpl.java` | 入库前调用一次 |
| `QuestionQualityCheckTest.java` | **新增**，14 个用例（含"不该报的不能报"的误报测试） |

## 三、扫描件 PDF 的识别

### 3.1 问题

扫描件（图片型 PDF）用 PDFBox 抽文本，结果是**空字符串**。这跟"这份 PDF 确实是空的"没法区分。

用户的体验是：上传 → 等一会儿 → 看到"解析出 0 道题 / 文件格式无法识别"，**不知道该改格式还是该检查文件**，只能反复重传同一个文件。

### 3.2 解法

`PdfTextReader` 增加一次**文字层体检**：

```java
// 每页文字少于 30 个 → 认为"几乎没有文字层"
boolean looksScanned() {
    return pageCount > 0 && text.length() / pageCount < MIN_CHARS_PER_PAGE;
}
```

命中时给一句准确的话：

> 这份 PDF 几乎没有文字层（12 页只有 87 个字符），看起来是扫描件/图片版。图片里的文字无法直接提取，请改用原始的 txt / docx，或先用 OCR 转成文字后再导入。

**两个设计取舍**：

1. **只提示、不拒绝**：万一真是内容极少的 PDF，也只是多一句话，不会挡住正常流程
2. **在规则解析失败后立刻拦截**：因为扫描件没有文字层，**AI 也救不了**（它拿到的同样是空文本）。不拦的话会白跑一次模型调用（花钱 + 等待）

### 3.3 顺带记录的上游局限

`PdfTextReader` 里的注释补了一条调研得到的事实：

> `setSortByPosition(true)` 对**双栏** PDF 处理不好，这是 PDFBox 的已知问题
> （上游 issue [PDFBOX-2637](https://issues.apache.org/jira/browse/PDFBOX-2637)，2015 年提出，**至今仍是 Open**）。

写进注释是因为：后来人会以为"设置了 sortByPosition 就没问题了"，其实不是。

### 3.4 改动文件

| 文件 | 改动 |
|---|---|
| `PdfTextReader.java` | 新增 `readWithDiagnostics()` + `Result` record（`looksScanned()` / `scannedHint()`） |
| `BanksServiceImpl.java` | PDF 走带体检的读取；扫描件优先给出准确提示 |

## 四、顺手修掉的小问题

这批修复里还清了 11 处死代码，其中值得单独说的是两个：

### 4.1 `AiErrors.mask()` 的潜在 NPE

```java
// 改之前：config 为 null 时，这一行会抛 NullPointerException
return config.apiKey() == null ? msg : msg.replace(config.apiKey(), "***");
```

虽然当前没有调用方传 null，但一个"脱敏工具"自己抛 NPE 很讽刺 —— 而它恰恰是在**处理异常**的路径上被调用的（异常处理里再抛异常，排查起来很难）。加了 null 判断。

### 4.2 `debugHeader()` —— 死代码里的死代码

`QuestionParser.debugHeader()` 是个 12 行的调试方法，方法体只有两个 `System.out.println`，唯一引用在测试文件里**已经被注释掉**。连它服务的那个测试文件（`Text.java`）本身也是死代码：

- 0 个断言
- 硬编码了本机绝对路径 `D:\FinalText\题库脚本源码\...` → **换任何一台机器都必然失败**

删掉它俩之后，测试基线才真正"干净" —— 这是后续所有量化改进的前提。

## 五、面试可能怎么问

按可能被追问的顺序整理，**每条都能在代码里找到对应**：

### Q1：这个 bug 你是怎么发现的？

> 不是靠报错发现的 —— 是**读代码 + 查配置**定位的。我先确认 AI 输出是用 Jackson 直接解析的，再全项目 grep 确认**没有任何自定义 Jackson 配置**（所以走严格规范），最后看清洗函数只处理 markdown 围栏、不碰转义。
>
> 这里有个反直觉的点：这个 bug **有一半情况不报错**。`\f` `\b` `\v` 在 JSON 里是合法转义，所以 Jackson 会把 `\frac` 静默解析成「换页符 + rac」—— 程序不崩，数据坏了。

### Q2：为什么不能简单地"把所有反斜杠都翻倍"？

> 因为 `\n` `\t` `\"` `\\` 这些是**真转义**，翻倍会破坏它们 —— 一个真正的换行会变成字面量「反斜杠 + n」两个字符。
>
> 所以必须逐字符判断"这个反斜杠是不是合法转义的开始"。

### Q3：为什么第一版修复不管用？

> 因为我把问题理解成"修复非法转义"了。`\alpha` 确实修好了，但 `\frac` 照样坏 —— **`\f` 是合法转义**，按"保留合法转义"的规则走它被原样放过，到 Jackson 那里还是被解析成换页符。
>
> 这让我想明白：**这不是转义合法性的问题，而是 JSON 的转义语义和 LaTeX 命令语法天然冲突**。只要算法尊重 JSON 语义，`\frac` 就一定会坏。

### Q4：那怎么区分"真的换页符"和"LaTeX 的 \f"？

> 用一条启发式：**控制转义后面紧跟一个小写字母 → 当 LaTeX 处理**。因为真的换页符后面不会正好跟一个字母（典型是"第一页`<FF>`第二页"或行尾）。
>
> 我知道这是启发式、不是严格解 —— 但严格解不存在，因为在 JSON 语义里这两个东西**本来就无法区分**。

### Q5：那 `\times` 怎么办？

> **修不了，而且是我刻意不修的。** `\t` 在正文里是真会用到的字符（制表符），如果按"`\t` 后面跟字母就当 LaTeX"来修，就会把正常的「TAB + imes」误改成 `\times`。
>
> 所以这一类的解法是从**源头**约束：在系统提示词里明确要求模型把 LaTeX 反斜杠写成 `\\`。代码只做能安全做的兜底。
>
> 我不认为"全都修好了"是真话，所以这个局限写在注释里。

### Q6：为什么专门写一个 `AiJsonRepair` 工具类？

> 因为**三条 AI 路径都有这个 bug**：结构化抽取走 `objectMapper.readTree`，逐题补解析和知识点总结走 Spring AI 的 `BeanOutputConverter`。
>
> 我特意反编译了 `BeanOutputConverter`（`javap -p`）确认它内部就是普通 `ObjectMapper`，自带的清理器只有 `MarkdownCodeBlockCleaner` 和 `WhitespaceCleaner`，**不碰转义**。所以三条路径得共用同一份修复逻辑。

### Q7：「答案越界」这个检查有什么用？

> 它是**免费的错误探针**。答案 D 但选项只有 A/B/C —— 这不可能是题目本身如此，**一定是切题切错了**。
>
> 所以跑一次导入，日志就会告诉你「发现 12 处答案越界」，不用人工逐题核对。这是在没有 golden 数据集的情况下，最快拿到"数据健康度"的手段。

### Q8：为什么自检只打标、不阻断导入？

> 因为它的判据是**启发式**，会有误报（比如题目本身确实缺答案）。用它来决定"要不要入库"风险太大。
>
> 它的定位是**可观测性**，不是校验器。真正的入库门槛还是在原来的地方（题干空、判不出题型才跳过）。

### Q9：为什么砍掉了「题号跳号」检查？

> 做不了。`QuestionParser` 切题时已经把题号从题干里剥掉了，`RawQuestion` 也没保留原始题号，所以拿不到两个题号做比较。
>
> 我也可以从"两个块的起始行号差"去推断，但那会产生大量误报（题目之间有空行、有解析文字都很正常），反而让这个探针失去意义。所以**砍掉，并写明为什么**。

### Q10：这批改动怎么验证的？

> 三个层次：
> 1. **单测 34 个新用例**（修复逻辑 16 + 自检 14 + 原有 4 个补充），其中专门有一组是"不该报的不能报"的误报测试 —— 因为一个误报满满的检查等于没有检查
> 2. **测试里有"证明 bug 真实存在"的断言**：比如先断言 `\frac` **在修复前确实是坏的**，再断言修复后是好的。如果哪天有人"优化"掉了修复逻辑，这个测试会失败
> 3. **全量 `mvn test`**：65 个用例全绿（改之前是 31 个）

### Q11：Java 里有什么坑和这个有关？

> 有，而且我踩了：**Java 编译器在词法分析最早期就处理整个源文件的 `\uXXXX`，注释也不例外**（JLS 3.3）。
>
> 我第一版代码编译不过，报 5 个「非法的 Unicode 转义」，全在我自己写的 Javadoc 里 —— 我为了举例写了 `\uXXXX`，编译器真去解析它。
